# AI-Native SDLC · 测试与质量保障

测试与质量保障阶段以真实用户路径的端到端测试界定功能是否完成，借助单元、属性、差异、模糊、Expect 与确定性仿真构建快速回归防线，并在明确环境基线下核对设计承诺的性能与资源预算。

## 1. 阶段定位与测试证据规范

本章与第 4 章（验证）共同构成 AI-Native SDLC 的**正确性层**；同时负责核对设计与实现阶段已经承诺的性能与资源预算：

**意图与需求 → 设计与架构 → 实现 → 验证 →「测试与质量保障」→ 集成与交付 → 持续演进**

| 维度 | 核心约定 |
|------|----------|
| 主回答的问题 | 系统在具体业务场景、随机边界输入与约定负载压力下，行为与资源表现是否符合验收及预算要求 |
| 与第 4 章的协同 | 验证章确立基于真实用户路径的运行时基准与高风险形式化性质；本章着重于场景回归网、输入面探索、断言质量评估以及性能与资源门禁 |
| 防范同源盲区 | 当 Agent 同时撰写实现代码与局部测试时，测试容易复刻实现中的错误假设；必须依托独立基准、跨层检查与客观证据对抗同源共错 |

### 核心原则

- **完成标准与局部回归分离**：由端到端用户路径判定功能是否真正完成，由单元测试保证高频局部回归速度。
- **验收与已承诺预算双驱动**：功能正确性与设计阶段承诺的性能指标各自成门禁，不可互相替代或混为一谈。
- **失败信息可直接定位问题**：并发调度优先追求可控复现（DST），性能数据必须附带完整环境标签与基准版本。
- **显式声明未覆盖区域**：不允许把“流水线全绿”当作“所有业务性质与性能假设均已成立”的同义词。

### 1.1 测试证据记录字段

向交付门禁提交的每项重要测试结论，均应能回答以下五项性质级证据字段：

| 字段 | 记录要求 |
|------|----------|
| 性质 / 验收 / 预算 ID | 明确关联上游意图验收条款、接口契约或 PERF / 资源预算编号 |
| 测试手段 | 标注单元、表驱动、PBT、Fuzz、差异测试、Expect、DST、负载或浸泡测试 |
| 运行结果 | 通过 / 失败 / 超时或预算未运行 |
| **未覆盖范围** | 明确声明本轮测试未触及的输入边界、故障组合或生产环境条件 |
| 证据指针 | 指向可重放的日志、测试报告、确定性随机种子、截图或指标导出路径 |

## 2. 测试分层与完成标准

完整的测试体系需要覆盖从纯函数逻辑到跨节点恢复、再到长稳资源消耗的各个层面：

| 测试层级 | 核心检验目标 | 典型运行频次 |
|----------|--------------|--------------|
| 单元测试 / 表驱动 | 验证纯函数逻辑、分支边界与局部不变量 | 内环开发实时运行 |
| Expect / 行为轨迹测试 | 以可读快照比对复杂状态输出或接口交互演化 | 内环及提交前运行 |
| 属性测试（PBT） | 检验跨大规模随机输入始终成立的通用不变式 | 提交前 / 合并前运行 |
| 模糊测试（Fuzz） | 探测解析器、协议边界与异常载荷的健壮性 | 合并前定时跑或夜间持续运行 |
| 差异测试 / 变异测试 | 验证新旧实现一致性；评估测试套件本身的断言有效率 | 差异随重构跑；变异按预算限时跑 |
| 库级仿真 / 确定性仿真（DST） | 在可控随机种子下复现网络分区、时钟漂移与故障重启 | 合并前或高风险流水线运行 |
| 端到端 / 集成路径测试 | 在接近真实的组装环境中校验完整用户操作链路 | 提交前 / 合并门禁必跑 |
| **基准 / 负载 / 压力 / 浸泡测试** | 核对延迟、吞吐、退化背压与长稳资源泄漏预算 | 按预算归属在合并或发布前运行 |
| 结构复杂度与健康度度量 | 监控圈复杂度、模块耦合度与测试维护成本 | CI 定期扫描预警 |

### 2.1 单元测试与端到端测试的职责界线

在实际工程中，必须严格区分单元测试与端到端测试的门禁权重：

- **单元测试（快且稳定，但存在同源局限）**：执行速度极快、故障隔离清晰，非常适合验证纯算法逻辑与内部工具函数。但在 AI-Native 研发模式下，Agent 往往会依据自己对需求的理解同时编写实现与单元测试，极易出现“所有单元测试绿灯，但真实用户路径完全不可用”的假阳性陷阱。
- **端到端测试（最难被局部假阳性欺骗）**：端到端测试模拟真实入口启动完整链路，核心路径要么真正走通，要么明确失败。失败诊断最好附带界面截图、接口返回与关键状态快照，避免只有一句模糊的超时信息。考虑到其执行较慢且易受外部环境干扰，适合部署在提交前与合并前门禁，而不必强塞入每一次微小的编码步进中。
- **门禁权重约定**：**真实用户路径的端到端证据决定“任务是否真正完成”，单元测试决定“日常局部修改的回归速度”**。如果项目起步阶段资源有限、只能先建一种完成定义，应当优先建立端到端用户路径测试（具体运行方式参见第 4 章的运行时验证），再逐步补齐单元测试覆盖。

属性测试可以补充人类未曾设想的边界组合，差异测试可以拦截系统迁移时的细微走样，但**二者均不能替代对真实端到端用户路径的直接检验**。

## 3. 关键正确性测试方法与变异预算

为避免正确性测试流于表面，各专项方法应各司其职、与第 4 章的性质编号对齐：

- **属性测试（PBT）**：从接口契约与业务不变式中提炼“对所有合法输入均应成立”的通用规律（如往返编码一致、状态操作幂等、余额守恒），借助随机生成与反例收缩（Shrinking）定位最小失败案例。
- **差异测试（Differential Testing）**：在重构替换、跨语言重写或存在规范参考模型时，将同一组输入同时喂给新实现与基准对照版本，直接比对最终状态与关键输出差异。
- **模糊测试（Fuzzing）**：面向外部输入解析、权限令牌处理或二进制协议边界注入畸形与非预期载荷，重点捕捉崩溃、死循环与未处理异常。
- **Expect / 轨迹快照测试**：将复杂多步状态变化或命令行/编译输出固化为人类易于快速审查的对比文本，借助逻辑差异而非逐行代码实现高效审阅。
- **确定性仿真测试（DST）**：依托第 2 章预留的可插拔非确定性边界，通过注入可控虚拟时钟、随机网络延迟与磁盘故障来探索并发恢复漏洞；一旦暴露反例，必须归档固定随机种子作为永久回归保护。

### 3.1 变异测试的作用范围与预算控制

当实现代码与测试代码同由 Agent 生成时，容易出现“断言流于形式、代码改动哪怕弄坏关键条件测试依然全绿”的同源失察问题。**变异测试（Mutation Testing）检验的是测试套件自身的缺陷检出能力（即断言是否真正有效），而非直接证明产品业务正确**——凡是能够明确写成属性断言或形式化性质的逻辑，不应退而用变异测试去近似替代。

此外，在大型仓库中执行全量变异测试往往耗时长达数小时，**绝不能放入开发内环循环**。在工程落地时，必须严格遵守以下三项范围与预算约束：

1. **只变异本次变更覆盖的代码**：仅针对本次提交涉及的函数、分支或改动模块生成变异体，严禁动辄扫荡全库历史代码。
2. **优先高信号变异算子并跳过无效变体**：优先执行条件边界反转、返回值篡改与逻辑连接词替换等高价值变异，自动跳过无法通过编译的变异体及语义等价变异体。
3. **限时限量、禁止内环阻塞**：开发内环不运行变异测试；仅在提交前或合并前对本次改动模块设置严格的时间上限或最大变异体数量预算，全仓库规模的深度变异审计仅安排在夜间流水线面向极少数核心模块运行。对于因触及时间或数量上限而未能跑完的变异体，**必须诚实记为“未覆盖”**：既不得伪造成“全部通过”，也不得仅因预算耗尽而误判为门禁失败。

除非目标模块体积极小且已事先锁定了可预测的计算预算，否则不建议将变异得分率设为全仓默认的硬性阻断红线。

## 4. 性能与资源预算测试

性能测试不是项目上线前的临时调优，而是对第 2 章设计预算的系统性核对：

| 测试类型 | 核心核对目标 |
|----------|--------------|
| 微基准测试（Microbenchmark） | 监控关键热路径的耗时与内存分配回归（须严格控制机器噪声） |
| 负载测试（Load Test） | 核对在目标并发量与预期业务吞吐下，P95/P99 延迟与 CPU 占用是否符合预算 |
| 压力测试（Stress Test） | 检验超过额定负载时，系统的背压拒绝、排队限流与降级策略是否按设计生效 |
| 浸泡测试（Soak Test） | 在长时间持续运行下捕捉内存泄漏、连接/文件句柄泄漏与长尾延迟漂移 |
| 资源受限测试 | 在人为收紧内存上限、CPU 配额或 FD 数量时，确认系统是否能够安全失败（Fail-Closed） |
| 客户端专项测试 | 核查冷启动耗时、崩溃恢复速度、进程间通信延迟及前后台 CPU/内存峰值快照 |

### 执行规则

1. **区分阻塞门禁与探索性压测**：只有设计基线中**明确承诺**的性能与资源预算（带有唯一预算 ID）才可设为合入或发布阶段的阻塞门禁；其余探索性极限摸底测试安排在夜间或独立流水线执行。
2. **环境与构建元数据必须完备**：每一份性能对比数据都必须绑定硬件机型、操作系统、构建优化参数及对比基线版本；缺失环境标签的性能数字视为无效证据。
3. **禁止混淆性能与正确性**：吞吐或延迟基准达标，绝不意味着并发协议安全或功能状态正确。
4. **严禁通过放松安全边界换取性能指标**：如果出现为了跑赢耗时阈值而拉长外部超时或关闭 Fail-Closed 校验的情况，门禁直接判定失败。
5. **故障组合下安全优先**：当性能测试与断网、OOM 等极端故障注入叠加时，首要断言系统能够安全失败并完整恢复，其次再核对降级期间的预算表现。

## 5. 规范执行流程与质量门禁

1. **汇集待测目标清单**：从意图基线、接口契约与设计预算中提取所有需要检验的验收条目、性质 ID 与 PERF 指标。
2. **按风险分配测试层级**：明确主链路端到端覆盖范围，为复杂逻辑分配 PBT / 差异测试 / DST，为热路径配置对应性能基准。
3. **运行测试闭环并收集客观证据**：由 Agent 在隔离环境下运行功能与预算测试套件，修复暴露出的真实缺陷并确保驱动留存可核查产物。
4. **编制性质覆盖与未覆盖报告**：逐项填写“已查范围”“未覆盖边界”与可重放指针。
5. **落实同源独立性防线**：对高风险路径采用基于真实用户操作、跨实现对照、独立规格或受控局部变异来打破实现-测试同源盲区。
6. **接入持续集成门禁**：将快慢测试分层接入 CI，确保本地执行路径与流水线门禁一致（耗时性能与浸泡测试可挂接独立流水线）。

### 质量门禁

- [ ] 主成功路径与核心验收场景均已建立自动化测试并与需求/性质 ID 映射
- [ ] **功能完成标准由真实用户路径的端到端证据界定**，单元测试不单独充当“已完成”依据
- [ ] 关键异常输入、权限拒绝与恢复失败路径均具备有效覆盖
- [ ] 关键通用不变式已通过属性测试（PBT）或等价机制检验
- [ ] 所有已承诺的性能与资源预算均已完成核对测试（或已登记书面批准的延期）
- [ ] 性能测试报告包含完整硬件环境、构建选项与基线对比版本指针
- [ ] 高风险外部输入解析面已接入模糊测试（Fuzz），关键协作轨迹已建立 Expect 或仿真覆盖
- [ ] 分布式状态恢复或复杂异步场景已评估确定性仿真（DST）或书面接受残余风险
- [ ] 若运行变异测试：严格限定于本次改动范围并设定时间或数量预算，未跑完部分已标为“未覆盖”
- [ ] 当实现与测试同由 Agent 编写时，已落实独立性验证措施（端到端/差异/独立规格）或显式记录风险

## 6. 人机职责分工与本章小结

| 角色 | 本章主要工作 | 边界与注意事项 |
|------|--------------|----------------|
| Agent | 编写并维护多层测试集、端到端回归脚本与预算基准，运行测试闭环并输出覆盖账本 | 警惕测试围绕错误实现自圆其说；严禁通过删改断言、屏蔽不稳定用例或调整超时来敷衍门禁 |
| 人（HITL） | 重点审查端到端通过现场、未覆盖清单及性能基线趋势变化，合理分配审阅注意力 | 不要求人类逐行检查所有单测代码，而是核查“测试网是否真正独立检验了关键风险” |

### 本章小结

- 正确性证据与已承诺的性能预算共同构成交付前提，缺失环境与基线标签的性能数据不具备门禁效力。
- 端到端用户路径验证界定“功能是否完成”，单元测试服务于“快速发现局部退化”；变异测试仅用于衡量测试套件的断言有效率，必须在严格预算下远离开发内环。
