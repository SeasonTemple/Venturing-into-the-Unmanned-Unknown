# AI-Native SDLC · 测试与质量保障

## 1. 本章定位

测试关注「在具体场景下是否表现正确」，与《验证》章互补：  
验证偏向更强性质与设计/实现正确性；测试偏向场景行为与可回归的质量网。  
手段跨语言通用；具体框架随语言替换（Go `testing` / Rust `#[test]` / pytest / JUnit 等）。

### 基本原则

- 验收驱动  
- 分层建设、风险优先  
- **可执行规格优先**（表格 + 属性）  
- 可自动化、可维护  
- 结果可解释（失败要指向「哪个行为/契约错了」）  
- 测试质量本身可评估（变异测试等）  

---

## 2. 测试分层（语言中立）

| 层级 | 目标 | 特点 |
|------|------|------|
| 单元测试 | 局部逻辑正确 | 快、定位准；表驱动 |
| 属性测试（PBT） | 普遍性质成立 | 生成大量输入，挖边界 |
| 模糊测试（Fuzz） | 异常输入下的健壮性 | 崩溃、断言、内存错误 |
| 差异测试 | 多实现行为一致 | 重构、多 Agent、参考实现对比 |
| 集成测试 | 模块协作正确 | 发现边界与契约错误 |
| 端到端测试 | 用户路径正确 | 接近真实，成本较高 |
| 专项场景 | 风险路径可靠 | 并发、故障、超时、权限 |
| 测试质量评估 | 测试是否真有杀伤力 | 变异测试（进阶） |
| 代码健康度 | 复杂度可控 | 圈复杂度 / 认知复杂度等度量 |

---

## 3. 属性测试（Property-Based Testing）

用「永远应成立的性质」代替少量手写例子；工具自动生成输入（含边界）。

**写法原则：**

- 明确量化范围与合法输入（用生成器收紧）  
- 一个属性聚焦一件事；命名可读  
- 同时写正向性质与「不应发生」的负向断言  

**各语言常见方向（示例，非穷尽）：**

| 语言 | 代表库 / 机制 |
|------|----------------|
| Rust | `proptest` 等 |
| Go | `testing/quick`、`rapid` 等 |
| Python | Hypothesis |
| Java / JVM | jqwik、QuickTheories 等 |
| JavaScript/TS | fast-check 等 |
| C/C++ | 可与 libFuzzer 等结合的生成式思路 |

与验证章衔接：属性即可执行规格，也可作为后续形式化 postcondition 的草稿。

---

## 4. 模糊测试（Fuzzing）

对解析、编解码、协议处理等「输入面」极有效。  
许多语言已内置或一等支持（如 Go 原生 fuzz、Rust cargo-fuzz、libFuzzer/AFL++ 用于 C/C++）。  
发现的坏输入应固化为回归用例。

---

## 5. 差异测试（Differential Testing）

同一输入，多个「应一致」的实现，对比结果与错误行为。

**典型用途：** 旧 vs 新、Agent A vs Agent B、自研 vs 标准库/参考实现、跨语言参考实现。  
**要点：** 合法与非法输入都覆盖；比较成功结果与失败方式；非确定性需固定种子或抽象。  
差异失败是**规格补全信号**。

---

## 6. 变异测试（Mutation Testing）

故意改坏代码（变异体），看现有测试能否杀掉。评估**测试套件强度**。  
多数主流语言有工具（如 PIT for JVM、mutmut / cosmic-ray for Python、Rust/Go 生态中的实验或第三方工具）。成熟度因语言而异，属**进阶可选**；建议在关键模块、测试已较充分后定期使用。

---

## 7. 复杂度与静态质量

- **跨语言：** Lizard 等可算圈复杂度、函数长度。  
- **语言内：** 各生态 linter/分析器（如 Rust clippy、Go golangci-lint + gocyclo、C/C++ 各类静态分析、ESLint 复杂度规则等）。  
- 作用：防止实现过度复杂；与「设计阶段限制函数长度/状态」互补。golangci-lint 等是**聚合器**，不是某一单一度量工具的「升级版」。

---

## 8. 规范执行流程

1. 从验收标准生成主路径测试（表驱动 + 正反例）  
2. 按模块补齐单元测试  
3. 对通用性质增加**属性测试**  
4. 对输入面增加**模糊测试**  
5. 关键路径增加**差异测试**（多实现或重构）  
6. 构建集成、端到端与风险场景  
7. （可选）变异测试评估测试杀伤力  
8. 复杂度与静态门禁纳入 CI  
9. 维护测试资产；意图/契约变更时同步更新  

### 质量门禁

- [ ] 主要验收标准均有对应自动测试  
- [ ] 关键模块有单元级保护  
- [ ] 关键性质有属性测试或等价可执行规格  
- [ ] 高风险输入面有 fuzz 或等价加固  
- [ ] 高风险场景有专门用例（含并发/故障）  
- [ ] 测试可在 CI 自动执行  
- [ ] 失败信息能指向行为或契约  
- [ ] （建议）关键区做过差异或变异抽检  
- [ ] 复杂度/静态门禁未无故放松  

---

## 9. 简洁实例

写锁验收：  
表格用例 → 单元测互斥 → 属性「同一资源不同时被两持有者写」→ 两实现差异测试 → 集成/端到端 → CI；可选变异测测试强度；用该语言的复杂度工具限制锁管理函数复杂度。

---

## 10. 常见反模式

| 反模式 | 正确做法 |
|--------|----------|
| 只测成功路径 | 成功与关键失败成对 |
| 全靠端到端 | 分层测试 |
| 测试实现细节 | 优先测行为与契约/属性 |
| 测试与需求脱节 | 从验收标准与可执行规格映射 |
| 无限加自然语言规格 | 冲突时优先补表格/属性/差异用例 |
| 忽视测试自身质量 | 关键路径考虑变异或审查 |
| 绑死单一语言工具名 | 按项目语言替换等价工具 |

---

## 11. Agent 执行要点

1. 先写能判定验收标准的**可执行**测试（表格 + 属性）  
2. 失败信息要指向「哪个行为错了」  
3. 高风险路径优先补场景、fuzz 与差异对比  
4. 多 Agent 实现时用差异测试暴露理解冲突并反哺规格  
5. 按**目标语言**选择具体测试框架与 fuzz/变异工具  
6. 意图或契约变更后同步更新测试  

---

## 12. 本章要点

- 测试是最广泛的行为质量网；与验证分工明确  
- 以验收标准与可执行规格为源头，按风险分层；**手段跨语言，工具按语言落地**  
- 属性测试、模糊测试、差异测试、变异测试、复杂度度量是对传统金字塔的重要补充  
- 规格无法穷尽实现细节时，用可执行用例 + 快速反馈闭环管理 Agent 歧义
