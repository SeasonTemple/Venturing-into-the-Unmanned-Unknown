# AI-Native SDLC · 测试与质量保障

## 1. 本章定位

测试关注「在具体场景下是否表现正确」，与《验证》章互补：  
验证偏向更强性质与设计/实现正确性；测试偏向场景行为与可回归的质量网。  
手段跨语言通用；具体框架随语言替换。

### 基本原则

- 验收驱动  
- 分层建设、风险优先  
- **可执行规格优先**（表格 + 属性）  
- **快速、可读的反馈**（对人与 Agent 同等重要）  
- 可自动化、可维护、失败可解释  
- 测试质量本身可评估（变异测试等）  
- 分布式/并发路径优先考虑**可复现**（确定性仿真），而非仅依赖真实环境的偶发失败  

---

## 2. 测试分层（语言中立）

| 层级 | 目标 | 特点 |
|------|------|------|
| 单元测试 | 局部逻辑正确 | 快、定位准；表驱动 |
| Expect / 快照式行为测试 | 行为轨迹可读、可 diff | 输出嵌入规格，利于人与 Agent 理解 |
| 属性测试（PBT） | 普遍性质成立 | 生成大量输入，挖边界 |
| 模糊测试（Fuzz） | 异常输入下的健壮性 | 崩溃、断言、内存错误 |
| 差异测试 | 多实现行为一致 | 重构、多 Agent、参考实现对比 |
| 库级确定性仿真 | 组件协作在可控时钟/网络下可复现 | 毫秒～秒级反馈 |
| 全系统确定性仿真（DST） | 整系统故障与调度可复现 | 高成本、高收益（分布式/存储/协议） |
| 集成 / 端到端 | 模块协作与用户路径 | 接近真实，成本较高 |
| 专项场景 | 并发、故障、超时、权限 | 可与 DST/混沌互补 |
| 测试质量评估 | 测试是否有杀伤力 | 变异测试（进阶） |
| 代码健康度 | 复杂度可控 | 圈/认知复杂度等度量 |

---

## 3. 属性测试（Property-Based Testing）

用「永远应成立的性质」代替少量手写例子；工具自动生成输入（含边界）。

**写法原则：** 明确量化范围与合法输入；一属性一事；正向与负向断言兼备。  
各语言有对应库（如 Hypothesis、proptest、rapid、jqwik、fast-check 等）。  
与验证章衔接：属性即可执行规格，也可作形式化后置条件的草稿。

---

## 4. 模糊测试（Fuzzing）

对解析、编解码、协议处理等「输入面」极有效。坏输入应固化为回归用例。  
与 DST 分工：fuzz 擅长**内部逻辑/输入面**；DST 擅长**外部非确定性**（时间、调度、网络、故障）。

---

## 5. 差异测试（Differential Testing）

同一输入，多个应一致的实现，对比结果与错误行为。  
多 Agent 实现冲突时尤其有用；失败是规格补全信号。

---

## 6. Expect 测试（行为轨迹可读）

**含义：** 运行代码，把人类可读的输出（日志、状态摘要、协议轨迹）嵌入测试源；失败时呈现与期望输出的 **diff**，并可一键接受更新。

**价值（对人与 Agent）：**

- 行为被「写进仓库」，承载意图，而不只是 pass/fail  
- 文本轨迹比纯布尔断言更易审阅与对话  
- 与库级仿真结合时，可在毫秒级看到 client/proxy/server 缠绕后的时间线  

**注意：** 输出必须**刻意设计成可读**；无结构的 dump 没有价值。适合「点按即崩」的脆性系统上的精心触点，与属性测试互补，而非替代。

（各语言有 snapshot / expect / golden file 等同类机制，名称因生态而异。）

---

## 7. 确定性仿真测试（DST）

### 7.1 是什么

将**应用**放在**可控仿真环境**中运行：由测试侧控制时钟、调度/交错、随机源、网络与存储延迟、进程崩溃等非确定性来源，使  

**同一初始种子 → 同一事件轨迹（可完整重放）。**

从而：大量探索故障与交错；一旦发现违反不变量的轨迹，用同一种子稳定复现并调试。

这不是「带种子的普通随机测试」，而是**把环境换成仿真器后的可复现调试管线**。

### 7.2 两个粒度（技术中立）

| 粒度 | 做法要点 | 典型收益 |
|------|----------|----------|
| **库级 / 组件级** | 将时钟、网络、服务发现等依赖可插拔，用内存实现替代真实 IO | 反馈可达毫秒级；看清协作时间线 |
| **全系统** | 多节点/多组件在同一受控运行时（或确定性 hypervisor）中仿真，注入网络/磁盘/进程故障 | 挖出真实环境极难稳定复现的并发与恢复缺陷 |

实现路径因项目而异：设计期把非确定性边界可插拔；或使用确定性运行时/仿真平台。**不绑定某一厂商或某一语言。** 业界常见实践来源包括数据库与分布式系统工程（如以可插拔仿真为核心的整系统测试、确定性 hypervisor 等），原则可迁移到自研仿真器。

### 7.3 四类须控制的来源

1. **并发与调度**（谁先跑）  
2. **时间**（虚拟时钟，可快进）  
3. **随机性**（统一种子）  
4. **故障注入**（丢包、延迟、崩溃、慢盘等）  

### 7.4 何时值得上

- 分布式协议、复制、共识、存储引擎、复杂状态机  
- 故障恢复与部分失败是产品正确性的一部分  
- 真实集群上「偶发、不可复现」的 bug 成本高  

普通 CRUD 与纯函数逻辑：属性测试 + 单元/集成通常更划算。  
混沌工程（真实环境加压）与 DST **互补**：前者问「线上能否扛住」；后者问「这条失败轨迹能否精确重放」。

### 7.5 与形式化 / 属性测试的关系

- 模型检查（如 TLA+）：设计空间穷举/反例  
- 属性测试：逻辑性质 + 生成输入  
- DST：实现级整系统/库级轨迹 + 故障 + **可重放**  
三者解决不同层的问题，可组合而非互相替代。

---

## 8. 变异测试与复杂度

变异测试评估测试套件杀伤力；复杂度度量防止实现失控。成熟度因语言而异，关键模块优先。

---

## 9. 规范执行流程

1. 从验收标准生成主路径测试（表驱动 + 正反例）  
2. 补齐单元测试；对关键行为增加 **Expect/可读轨迹** 测试  
3. 通用性质 → **属性测试**；输入面 → **模糊测试**  
4. 多实现/重构 → **差异测试**  
5. 协作与时间敏感路径 → **库级确定性仿真**  
6. 分布式/恢复关键路径 → 评估 **全系统 DST**  
7. 集成、端到端与风险场景  
8. （可选）变异测试；复杂度/静态门禁入 CI  
9. 意图或契约变更时同步更新测试资产  

### 质量门禁

- [ ] 主要验收标准均有对应自动测试  
- [ ] 关键模块有单元级保护  
- [ ] 关键性质有属性测试或等价可执行规格  
- [ ] 高风险输入面有 fuzz 或等价加固  
- [ ] 高风险协作路径有可读行为轨迹（Expect 类）或库级仿真  
- [ ] 分布式/恢复关键路径已评估 DST 或等价可复现手段  
- [ ] 测试可在 CI 自动执行；失败信息能指向行为或契约  
- [ ] （建议）关键区做过差异或变异抽检  
- [ ] 复杂度/静态门禁未无故放松  

---

## 10. 简洁实例

写锁 / 会话协调：  
表格用例 → 单元互斥 → 属性守恒 → Expect 打印持锁时间线 → 库级仿真加速时钟与丢包 →（若多节点）DST 注入节点重启并断言恢复不变量 → CI。

---

## 11. 常见反模式

| 反模式 | 正确做法 |
|--------|----------|
| 只测成功路径 | 成功与关键失败成对 |
| 全靠端到端 | 分层测试 |
| 测试实现细节 | 优先测行为与契约/属性 |
| 测试与需求脱节 | 从验收标准与可执行规格映射 |
| 不可复现的「偶发」失败只靠重跑 | 控制时间/调度/随机源或上 DST |
| 无结构 dump 当 Expect | 刻意设计可读轨迹 |
| 普通业务强上全系统 DST | 按风险选用库级仿真或属性/集成 |
| 用混沌替代一切可复现手段 | 混沌与 DST 分工：存活 vs 重放 |
| 绑死单一语言或单一仿真产品 | 按原则选型，工具可替换 |

---

## 12. Agent 执行要点

1. 先写可判定验收标准的可执行测试（表格 + 属性 + 必要时 Expect）  
2. 失败信息与轨迹要让人/Agent 能理解「错在哪条行为」  
3. 高风险路径优先可复现手段（仿真种子、固定随机源）  
4. 多 Agent 实现用差异测试暴露冲突并反哺规格  
5. 按目标语言与系统形态选择框架；DST 按风险启用，不默认全仓  
6. 意图或契约变更后同步更新测试  

---

## 13. 本章要点

- 测试是最广泛的行为质量网；与验证分工明确  
- 可执行规格 + 快速可读反馈（含 Expect）放大人与 Agent 的杠杆  
- **确定性仿真测试**把「偶发故障」变成「可重放轨迹」，适合分布式与恢复路径  
- 属性 / fuzz / 差异 / 变异 / DST / 复杂度度量按风险组合，不互相替代  
- 手段跨语言、跨厂商；原则中立，落地按生态选型
