# AI-Native SDLC · 测试与质量保障

## 1. 本章定位

测试关注「在具体场景下是否表现正确」，与《验证》章互补：  
验证偏向更强性质与设计/实现正确性；测试偏向场景行为与可回归的质量网。

### 基本原则

- 验收驱动
- 分层建设、风险优先
- **可执行规格优先**（表格 + 属性）
- 可自动化、可维护
- 结果可解释（失败要指向「哪个行为/契约错了」）
- 测试质量本身可评估（变异测试等）

---

## 2. 测试分层

| 层级 | 目标 | 特点 |
|------|------|------|
| 单元测试 | 局部逻辑正确 | 快、定位准；表驱动 |
| 属性测试（PBT） | 普遍性质成立 | 生成大量输入，挖边界 |
| 差异测试 | 多实现行为一致 | 重构、多 Agent、参考实现对比 |
| 集成测试 | 模块协作正确 | 发现边界与契约错误 |
| 端到端测试 | 用户路径正确 | 接近真实，成本较高 |
| 专项场景 | 风险路径可靠 | 并发、故障、超时、权限 |
| 测试质量评估 | 测试是否真有杀伤力 | 变异测试（进阶） |
| 代码健康度 | 复杂度可控 | Lizard / gocyclo / golangci-lint 等 |

---

## 3. 属性测试（Property-Based Testing）

用「永远应成立的性质」代替少量手写例子；工具自动生成输入（含边界）。

**写法原则：**

- 明确量化范围与合法输入（用生成器收紧）
- 一个属性聚焦一件事；命名可读（如 `Prop_TotalBalanceConserved`）
- 同时写正向性质与「不应发生」的负向断言

**Go 示例方向：** 标准库 `testing/quick`；更推荐 `rapid` 等。  
与验证章衔接：属性即可执行规格，也可作为后续形式化 `ensures` 的草稿。

---

## 4. 差异测试（Differential Testing）

同一输入，多个「应一致」的实现，对比结果与错误行为。

**典型用途：**

- 旧实现 vs 新实现（重构）
- Agent A 生成 vs Agent B 生成
- 自研 vs 标准库 / 参考实现

**Go 模板要点：** 生成输入 → 两套独立状态 → 分别调用 → 比较 `err` 是否同空、最终状态是否一致。  
非法与合法输入都要覆盖；非确定性逻辑需固定种子或抽象掉。

差异失败是**规格补全信号**：把冲突案例写进表格或属性。

---

## 5. 变异测试（Mutation Testing）

故意改坏代码（变异体），看现有测试能否杀掉。用于评估**测试套件强度**，而非直接找业务 bug。

- Go 生态有 `go-mutesting`、`gremlins` 等，成熟度与普及度低于 fuzz / staticcheck，属**进阶可选**。
- 建议：在关键模块、测试已较充分后定期跑；优先修「活下来的变异体」对应的测试空洞。

---

## 6. 复杂度与静态质量

- **Lizard**：跨语言圈复杂度等度量。
- **Go**：`gocyclo`、`gocognit`、`funlen` 等；实践中多用 **golangci-lint** 一站式集成（并非 Lizard 的「升级版」，而是更广的 linter 聚合器）。
- 作用：防止实现过度复杂，降低后续歧义与回归成本；与「设计阶段就限制函数长度/状态」互补。

---

## 7. 规范执行流程

1. 从验收标准生成主路径测试（表驱动 + 正反例）
2. 按模块补齐单元测试
3. 对通用性质增加**属性测试**
4. 关键路径增加**差异测试**（多实现或重构）
5. 构建集成测试与端到端、风险场景
6. （可选）变异测试评估测试杀伤力
7. 复杂度门禁（golangci-lint / Lizard 等）纳入 CI
8. 维护测试资产；意图/契约变更时同步更新

### 质量门禁

- [ ] 主要验收标准均有对应自动测试
- [ ] 关键模块有单元级保护
- [ ] 关键性质有属性测试或等价可执行规格
- [ ] 高风险场景有专门用例（含并发/故障）
- [ ] 测试可在 CI 自动执行
- [ ] 失败信息能指向行为或契约
- [ ] （建议）关键区做过差异或变异抽检
- [ ] 复杂度门禁未无故放松

---

## 8. 简洁实例

写锁验收：  
表格用例（成功持锁 / 拒绝 / 超时）→ 单元测互斥 → 属性「同一资源不同时被两持有者写」→ 两实现差异测试 → 集成/端到端 → CI；可选变异测测试强度；gocyclo 限制锁管理函数复杂度。

---

## 9. 常见反模式

| 反模式 | 正确做法 |
|--------|----------|
| 只测成功路径 | 成功与关键失败成对 |
| 全靠端到端 | 分层测试 |
| 测试实现细节 | 优先测行为与契约/属性 |
| 测试与需求脱节 | 从验收标准与可执行规格映射 |
| 无限加自然语言规格 | 冲突时优先补表格/属性/差异用例 |
| 忽视测试自身质量 | 关键路径考虑变异或审查 |

---

## 10. Agent 执行要点

1. 先写能判定验收标准的**可执行**测试（表格 + 属性）
2. 失败信息要指向「哪个行为错了」
3. 高风险路径优先补场景与差异对比
4. 多 Agent 实现时用差异测试暴露理解冲突并反哺规格
5. 意图或契约变更后同步更新测试

---

## 11. 本章要点

- 测试是最广泛的行为质量网；与验证分工明确
- 以验收标准与可执行规格为源头，按风险分层
- 属性测试、差异测试、变异测试、复杂度度量是对传统金字塔的重要补充
- 规格无法穷尽实现细节时，用可执行用例 + 快速反馈闭环管理 Agent 歧义
