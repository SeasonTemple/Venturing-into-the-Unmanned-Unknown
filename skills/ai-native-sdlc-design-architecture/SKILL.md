# AI-Native SDLC · 设计与架构

设计与架构阶段在结构层面将“容易写错、难以验证”的自由度压缩到最小，通过明确的模块边界、严格的接口契约、可插拔的非确定性隔离以及可度量的性能预算，为后续实现与独立验证建立坚实基准。

## 1. 阶段定位与设计原则

在 AI-Native SDLC 生命周期中，设计与架构承接意图基线，并为实现与正确性层提供可直接核对的施工蓝图：

**意图与需求 →「设计与架构」→ 实现 → 验证与测试 → 集成与交付 → 持续演进**

传统架构往往以人类开发者的心智模型为中心；而在以 Agent 为生产主体的环境下，**良好的架构首先是一套能够持续约束 Agent 不犯低级错误的外部骨架**：

| 核心价值 | 工程体现 |
|----------|----------|
| 可分解 | 模块职责边界清晰，输入输出明确，Agent 可以在局部上下文内独立完成实现 |
| 可协作 | 多 Agent 并行开发时通过稳定契约衔接，显著降低跨模块修改冲突 |
| 可防错 | 依靠目录隔离、类型系统与校验边界，使常见错误在编译期或静态检查期即被拦截 |
| 可验证 | 高风险并发、状态流转与非确定性依赖被显式隔离，便于模型检查与仿真注入 |
| 可度量 | 关键路径的性能与资源预算作为一等设计要素，防止“功能正确但上线即崩溃” |

### 基本原则

- **意图驱动、边界优先**：先划定每个模块负责什么、不负责什么，再决定内部数据结构与技术实现细节。
- **结构防错优先于文档说教**：凡是能通过目录边界、类型定义或导入约束禁止的错误，不依赖注释或提示词去祈祷 Agent “多加小心”。
- **隔离非确定性依赖**：将时钟、随机数、网络 I/O 与外部存储抽象在可替换边界之后，为确定性测试与仿真扫清障碍。
- **预算与恢复显式化**：关键路径必须给出性能与资源预算（或显式声明“本阶段不作承诺”），并事先定义过载与失败时的安全退化策略。

## 2. 结构防错：边界隔离、契约与非法状态收紧

### 2.1 代码库是 Agent 跨轮次的真实记忆

在连续迭代中，Agent 并不会天然记住历史口头约定，**当前仓库的目录组织、既有接口与常见写法就是 Agent 下一次生成代码时直接模仿的样板**。如果仓库中充斥着绕过边界的临时捷径、互相耦合的循环引用或仅靠注释声明的脆弱约定，后续的 Agent 会在新改动中不断复制并放大这些坏模式。

因此，判断一项设计是否真正完成，应当反问自己：**“如果下一轮由一个新启动的 Agent 来修改或调用这里，它还能不能轻易写出同类错误？”** 如果答案是肯定的，说明结构约束尚未收紧到位。

### 2.2 让非法状态不可表示、让违规导入无法通过

- **目录与依赖边界物理隔离**：尽量按业务能力与职责划分独立目录与清晰导出面，通过静态依赖检查或包边界规则直接禁止跨层非法引用，而不是在文档里写“请勿直接访问内部表”。
- **利用类型与状态机收紧状态空间**：优先使用强类型、判别联合（Tagged Union）或显式状态机枚举来表达合法状态转换，使“未初始化却已提交”“已关闭仍可写入”等非法组合在类型层面根本无法构造；若所选语言缺乏强类型表达能力，则必须在边界入口处设置统一的运行时校验层与契约断言。
- **使正确用法成为最省力的路径**：设计接口时避免依赖调用方“记住先后顺序或隐藏前置条件”，将资源释放、锁续期或事务提交封装成难以用错的最小接口。
- **可插拔的非确定性边界**：将系统时钟、外部网络调用、文件系统、随机数生成器等非确定性源头抽象为显式接口或依赖注入点，使核心业务状态机能够脱离真实环境进行纯内存或确定性仿真测试。

## 3. 核心设计产物与深度控制

设计阶段的产出应当是可供实现直接消费、供验证直接核对的明确资产，而非仅供展示的抽象框图：

| 设计产物 | 承担的工程职责 |
|----------|----------------|
| 模块与职责边界 | 明确各组件的归属职责、调用方向以及禁止跨界承担的功能 |
| 接口契约 | 定义清晰的输入参数、输出结构、错误类型与前后置条件（参考 `templates/interface-contract-template.md`） |
| 类型与状态不变式模型 | 以类型系统或核心状态转换图约束合法状态空间，标明跨步必须保持的不变量 |
| 关键路径与风险视图 | 标出并发竞争、状态交错、权限校验以及性能热点的具体位置与下游验证去向 |
| 失败、恢复与背压策略 | 规定外部依赖超时、队列饱和、部分失败时的安全失败（Fail-Closed）与降级恢复路径 |
| 性能与资源预算表 | 针对关键路径给出延迟、吞吐、内存或句柄占用等可核对目标 |
| 可仿真边界说明 | 标明时间、网络与故障注入点，支撑测试层的 Expect 或确定性仿真（DST） |
| 架构决策记录（ADR） | 记录重大技术取舍的背景、备选方案、放弃理由与长期约束（参考 `templates/adr-template.md`） |

### 3.1 设计深度控制

并非所有模块都需要同等粒度的设计文档，推荐采用三层深度控制策略：

| 深度层级 | 适用情形 | 产出重点 |
|----------|----------|----------|
| 概念设计 | 项目初期方向对齐与模块切分 | 系统上下文、核心模块职责边界与主业务数据流 |
| 逻辑设计（默认基准） | 准备移交 Agent 进入日常编码实现 | 完整接口契约、状态定义、异常与背压路径、资源预算与测试注入边界 |
| 详细设计（按需下钻） | 仅针对高并发协议、核心算法或高风险热路径 | 精确的状态机迁移步骤、并发时序约束、锁协议及关键内存/计算路径 |

团队应以**逻辑设计作为默认交付标准**，仅对标识出的高风险路径下钻至详细设计，避免在普通业务 CRUD 上过度设计。

## 4. 性能与资源预算设计

在实现之后再去“看情况调优”，往往意味着需要推倒数据结构与并发模型。设计基线在功能正确性之外，**应当对关键路径在约定负载下的表现作出明确预算或明确豁免**：

| 预算维度的设计要求 | 具体说明 |
|--------------------|----------|
| 预算来源与豁免规则 | 直接对齐意图中的性能或体验目标；若当前迭代暂不承诺性能指标，须显式标注“本阶段未承诺”，严禁用“实现后再看”敷衍了事 |
| 典型度量维度 | 端到端延迟（含 P95/P99 分位）、吞吐量、峰值 CPU/内存占用、文件句柄与连接数、冷启动与故障恢复时间、客户端包体或内存上限 |
| 热点与瓶颈标注 | 提前识别潜在的计算热路径、共享锁竞争区、大对象频繁分配及同步阻塞调用点 |
| 饱和与背压设计 | 明确系统过载或资源接近上限时采取拒绝请求、有界排队还是有损降级；明确是否遵循 Fail-Closed 安全原则 |
| 可观测性前提 | 定义需提前预留哪些关键计时指标、采样钩子或资源计数日志，确保测试与运行阶段可核对预算 |
| 运行环境假设 | 标明预算所依赖的硬件规格、操作系统、网络条件及并发规模；客户端应用须区分实验室基线机与真实用户设备环境 |

**正确性与性能的协同边界**：超时、内存配额耗尽或队列满载时能否**安全失败并保持状态一致**，属于功能契约与安全性质问题，绝不可为了压榨指标而妥协；“在正常负载下处理足够快”则属于性能与资源预算问题。二者必须在设计阶段同时规划，在门禁阶段分别核查。

## 5. 规范执行流程与质量门禁

1. **提取设计与性能驱动因素**：从意图基线中梳理核心功能约束、非目标项、已知未知及性能预期。
2. **切分模块与依赖方向**：确定模块边界、职责清单与依赖层级，建立静态防跨界规则。
3. **编写核心接口契约**：明确关键接口的入参、出参、错误码与前后置条件。
4. **收紧状态空间与结构防错**：通过类型设计、状态机及入口校验消除非法状态与高频 Agent 易错用法。
5. **标注高风险路径与验证去向**：识别并发、状态机、权限及性能热点，指定其后续交由端到端验证、模型检查、属性测试还是仿真覆盖。
6. **设计失败、恢复与可插拔边界**：定义过载背压策略与非确定性依赖的隔离接口。
7. **敲定性能预算或显式未承诺**：完成关键路径的资源预算表，并标明所需的可观测探针。
8. **沉淀 ADR 并输出设计基线**：对重要架构取舍记录 ADR，确认所有产出可供下游实现与验证直接执行。

### 质量门禁

- [ ] 模块职责清晰，依赖方向单向且具备结构性边界约束
- [ ] 核心接口均具备无歧义、可判定的输入/输出/错误契约
- [ ] 关键非法状态已通过类型系统或统一边界校验予以排除
- [ ] 已识别的高风险路径均已明确标注下游验证、测试或仿真去向
- [ ] 外部失败、超时恢复与过载背压策略已明确定义（如 Fail-Closed 行为）
- [ ] 关键路径已设定可核对的性能与资源预算，或已获批准标为“未承诺”
- [ ] 时钟、网络与外部存储等非确定性依赖具备可插拔测试边界
- [ ] 关键架构取舍已形成 ADR 决策记录
- [ ] 已知的 Agent 高频误用场景已通过目录结构、类型或静态检查阻断，或已登记待收紧计划

## 6. 人机职责分工与本章小结

| 角色 | 本章主要工作 | 边界与注意事项 |
|------|--------------|----------------|
| Agent | 依据意图拆分模块、起草契约与状态模型、设计可插拔边界、识别预算热点并梳理历史易错点 | 不得在未授权的情况下更改业务目标；不得以“先实现跑起来”为由跳过契约与结构防错设计 |
| 人（HITL） | 评审模块边界合理性、裁决重大技术取舍（ADR）、核准性能预算与“未承诺”豁免项 | 不必在第一轮定死所有长期 SLA，但必须确认高风险路径都有明确的验证归宿 |

### 本章小结

- 架构设计在 AI-Native 时代的核心作用，不仅在于划分模块框图，更在于通过代码结构和类型契约把高频错误挡在外面。
- 非确定性隔离与性能资源预算是设计与架构的一等产出，必须在一开始就为后续验证、测试与安全交付铺平道路。
