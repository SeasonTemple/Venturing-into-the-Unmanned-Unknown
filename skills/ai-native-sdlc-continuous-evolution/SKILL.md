# AI-Native SDLC · 持续演进

持续演进阶段将运行期的监控信号、线上缺陷与人工审阅反馈转化为按根因精准路由的改进任务，在优先止损的前提下由 Agent 完成受控修复与回归资产补全，并有纪律地沉淀有效门禁与淘汰失效规则。

## 1. 阶段定位与演进原则

交付上线不是生命周期的终点，而是下一轮认知修正与质量加固的起点：

意图与需求 → 设计与架构 → 实现 → 验证与测试 → 集成与交付 → **「持续演进」** → （按根因回流至意图、设计、验证或测试）

在长期维护中，**Agent 依然是修复缺陷与迭代功能的主力执行者**，人类继续承担更新业务意图与 HITL 理解型裁决的职责，而回归测试、仿真种子与 CI 门禁则确保系统不会在演进中发生倒退。这个阶段真正稀缺的不是编码人手，而是**人类审阅者的注意力与整个代码库对后续 Agent 的长期可读性**。

### 基本原则

- **运行信号驱动**：依托线上告警、性能漂移监控、CI 失败模式与审阅意见发现真实缺口，不凭主观猜测重构。
- **先止损，后根治**：面对已影响真实用户的线上异常，优先回滚、降级或开关止损，恢复稳定后再进入根因排查。
- **按根因层级回流**：不把所有缺陷一律归咎于“某行代码写错了”，而是溯源至真正的失守层级（意图、设计、验证或实现）。
- **资产与行为同步演进**：每次修复都必须同步更新代码、回归测试、验证规格与文档，防止真源分裂。
- **保持代码库长期可理解**：避免演进过程中不断堆叠“打补丁式”特例，使系统结构持续保持清晰，以便后续 Agent 能稳定接手维护。

## 2. 问题分级与分层回流模型

发现问题后，必须先判定该缺陷究竟在哪一层失去了防线，再将其回流至对应层级进行系统性补强：

| 观察到的问题特征 | 应回流的主导层级 | 对应的改进与加固动作 |
|------------------|------------------|----------------------|
| 业务目标误解、产品边界遗漏或验收定义出错 | 第 1 章 意图与需求 | 澄清意图描述、补充正反例对照、将隐含规则写入验收基线 |
| 模块职责交叉、接口契约漏洞或状态不变式缺失 | 第 2 章 设计与架构 | 收紧接口边界与类型状态机，弥补非确定性隔离或背压设计缺陷 |
| 并发交错漏洞、协议竞态或活性约束被破坏 | 第 4 章 验证 | 补充端到端验证路径或模型检查反例分析，修正协议设计 |
| 局部算法错误、空值疏漏或错误码映射不当 | 第 3 章 实现 | 修复代码实现，并检查同一错误模式是否需转化为静态检查 |
| 边界用例漏测、随机异常或偶发不可复现故障 | 第 5 章 测试与质量保障 | 补入表驱动用例、属性测试、Expect 快照或归档 DST 仿真种子 |
| 发布顺序错误、配置漂移或监控阈值失灵 | 第 6 章 集成与交付 | 完善发布迁移校验、运行级告警门禁与自动化回滚脚本 |
| 代码腐化严重、交叉耦合上升或规则冲突堆积 | 设计层 + HITL 治理 | 安排专项结构收敛重构，清理过时规则与技术债 |

## 3. 理解型审阅、门禁沉淀与规则治理

把日常生产交给 Agent 之后，**高水平的理解型人工审阅与严格的门禁治理不但不能省去，反而变得更加关键**。因为 Agent 非常擅长局部修修补补地把红灯变绿、完成眼前指派的功能，却往往缺乏全局自觉去维护架构简洁性、控制重复代码与遏制跨边界硬编码。一旦代码库变得混乱，后续接入的 Agent 只会顺着既有的混乱模式越改越碎。

为此，团队在演进过程中应坚持以下治理实践：

| 治理实践 | 具体工程要求 |
|----------|--------------|
| 严控审阅粒度，尊重 HITL 带宽 | 拒绝一次提交包含数十处跨模块改动的大型 PR，坚持拆分为逻辑连贯、易于理解和回滚的小粒度变更栈 |
| 依托行为轨迹辅助理解 | 结合 Expect 输出对比、仿真运行轨迹与端到端差异展示代码影响，让人类不必盲读海量行级改动 |
| 区分全仓自动化扫描与 HITL 理解型审阅 | 重复模式、代码气味与风格检查交由 CI 与静态工具自动清扫；人类审阅专注系统演进方向、复杂性控制与高风险取舍 |
| **按严格门槛将缺陷模式沉淀为门禁** | **同一类缺陷或违规模式在项目中至少重复出现两次，并且能够从代码或配置文件的改动特征中客观识别时，才将其固化为 Lint 或 CI 门禁**；仅出现一次或高度依赖语义判断的经验，则保留在设计笔记或复盘记录中，避免过早引入脆弱的规则噪音 |
| **定期清理失效规则与不稳定测试** | 定期审计并删除已经过时、与当前架构不符的旧规则；对于长期无法稳定修复的偶发误报（Flaky）检查，应果断清理下线并书面记录原因与替代手段，防止门禁公信力被误报侵蚀 |
| 坚决拦截投机绕过行为（Reward Hacking） | 若发现改动通过删减断言、制造空测试或过度 Mock 来制造绿灯假象，CI 与 HITL 必须直接否决并登记整改 |

## 4. 规范执行流程与质量门禁

1. **采集并分级异常信号**：汇总线上报错、指标漂移、CI 红灯规律及 HITL 审阅批注，按影响范围定级。
2. **优先执行线上止损**：对生产受影响的变更果断实施回滚、降级或开关隔离，确保服务迅速恢复可用。
3. **溯源定位根因层级**：依据第 2 节模型确定根本原因（建议使用 `templates/postmortem-template.md` 记录复盘），避免仅停留在表层打补丁。
4. **由 Agent 实施小步受控修复**：在设计基线和结构防错原则内完成局部修复，保持改动可追溯、易审阅。
5. **补齐永久性回归保护**：同步新增能够稳定复现该故障的端到端测试、属性断言、确定性仿真种子或契约约束。
6. **有纪律地沉淀知识与检查**：判断该问题是否满足“重复出现两次且可识别”的门槛，决定是沉淀为自动化门禁还是精炼写入技能/设计文档，同时清理冲突的过期规则。
7. **恢复常态观测与周期审计**：观察线上指标回归基线，定期组织技术债收敛与门禁健康度排查。

### 质量门禁

- [ ] 线上或下游暴露的问题已先期止损，业务影响已控制在安全范围内
- [ ] 已明确判定问题所属的根因层级（而非默认全部归类为编码失误）
- [ ] 修复补丁已由 Agent 在边界内完成，并通过全部基线系统检查
- [ ] 已补齐对应的永久回归保护（端到端路径、单测、属性或可重放仿真种子），防止同类故障复发
- [ ] 复盘结论、文档说明与受影响资产已与代码真实行为同步更新
- [ ] 若新增自动化门禁，该缺陷模式确已满足“重复出现至少两次且可从变更中客观识别”的条件；本轮同步清理了已失效规则或长期不稳定的无效检查
- [ ] 涉及高风险模块或架构边界调整的修复变更，已通过 HITL 理解型审阅

## 5. 工程实例：线上偶发双写故障的回流闭环

**现象**：生产环境在高峰期偶发出现同一文档的修改记录被两个会话互相覆盖，但本地常规单元测试长期全绿，无法直接复现。

**闭环演进处置流程**：

1. **止损**：发布流水线检测到数据版本冲突告警后，立刻启用降级只读锁策略并回滚最近一次锁服务调度调整，切断受损范围。
2. **定级与溯源**：复盘排查确认根因并非“代码里漏写了 `if` 判断”，而是第 1 章曾登记为“已知未知”的**多机房时钟偏移与租约超时重叠**问题，属于设计契约与验证协议层的遗漏。
3. **受控修复与验证**：回流至设计层引入基于单调递增 Fencing Token 的存储写入栅栏校验；随后在验证层（第 4 章）补充有限步长的并发租约模型检查，并将线上捕获的故障时间线转化为测试层（第 5 章）可一键重放的确定性仿真（DST）种子。
4. **回归与门禁沉淀**：Agent 基于新契约修复存储网关与锁客户端实现，全部检查通过后合入；团队同时核对历史审阅记录，发现“存储写入未校验 Fencing Token”已发生过两次类似疏漏，遂在静态接口检查中新增一条规则：凡涉及共享文档持久化的方法签名，必须显式接收并校验版本令牌参数。
5. **收尾归档**：更新第 1 章意图基线中的“已知未知”状态为已锁定性质，归档精炼的复盘事实，关闭该演进周期。

## 6. 常见反模式对照

| 常见反模式 | 正确的工程演进做法 |
|------------|--------------------|
| 只顾着打补丁掩盖表层报错 | 依据第 2 节分层模型溯源，补齐结构约束与永久回归 |
| 在生产异常压力下直接在主干做大规模重构 | 坚持“先止损回滚、再隔离调查、最后小步受控修复” |
| 修改了系统行为却忘了更新测试与规格真源 | 确保代码、测试断言、验证模型与文档说明在同一变更中同步演进 |
| 复盘会议开完后经验仅停留在聊天记录中 | 将可验证的结论固化为回归用例、Lint 规则或设计契约 |
| 提交包含大量跨模块改动、令 HITL 无法审阅的大 PR | 拆分为逻辑清晰的变更栈，并附带端到端证据与行为差异摘要 |
| 因新改动导致旧测试红灯，遂顺手删掉或跳过旧测试 | 严格禁止；必须查明是业务预期变更（先改真源）还是新引入的回归 Bug |
| 仅凭全仓静态扫描绿灯替代人类的理解型架构审阅 | 扫描工具负责扫清低级气味，架构复杂性与关键风险仍须升级至 HITL 裁决 |
| 遇到线上问题后退回“由人重新接管编码、Agent 在旁围观” | 保持 Agent 的生产主体定位，通过补齐环境边界与独立门禁提升系统可靠性 |

## 7. 人机职责分工与本章小结

| 角色 | 本章主要工作 | 边界与注意事项 |
|------|--------------|----------------|
| Agent | 收集失败现场证据、按指定根因层级推进小步修复、补齐回归保护并清理关联文档 | 严禁把所有线上传来的异常一律当作局部实现 Bug 草率打补丁；门禁受阻即停下来上报 |
| 人（HITL） | 主持关键故障定级与架构腐化评估、执行理解型审阅、拍板哪些重复模式值得升级为门禁、审批废除无效规则 | 守护仓库的可读性与复杂度底线，警惕为了追求表面效率而不断积累无用规则和脆弱测试 |

### 本章小结

- 持续演进的标准闭环是：**采集运行信号 → 优先止损 → 按根因分层回流 → Agent 受控修复 → 补齐永久回归 → 沉淀门禁并清理冗余**。
- 代码、验证资产、回归测试与规格文档必须同步演化；自动化检查是规模化防线，但不能取代人类（HITL）对架构健康度与价值取舍的理解型裁决。
