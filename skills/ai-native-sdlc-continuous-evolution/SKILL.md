# AI-Native SDLC · 持续演进

## 1. 本章定位

**交付 →「持续演进」→（回到意图或设计）**

把运行中的信号，转化成下一轮受控改进。稀缺资源仍是**人的注意力与理解**；工具应放大杠杆，而非以「人不读代码」为目标。

### 基本原则

- 信号驱动
- 分层回流
- 先止损，后根治
- 资产同步（代码、测试、验证、文档一起变）
- 小步演进、可追溯
- **理解优先**：演进必须保持系统对人可理解，Agent 才可持续有效

---

## 2. 问题回流模型

| 问题类型 | 回流层级 |
|----------|----------|
| 目标理解错误 | 意图层 |
| 结构、契约或不变量错误 | 设计层 |
| 协议/并发性质被打破 | 验证层 |
| 局部逻辑错误 | 实现层 |
| 场景覆盖不足、不可复现失败 | 测试层（含 Expect/DST 种子） |
| 发布或配置问题 | 交付层 |
| 仓结构腐化、交叉复杂度上升 | 设计 + 审阅纪律 |

---

## 3. 人机协作下的 Code Review

Agent 时代审阅**更重要**，而非更可省：

- Agent 善于把「红灯变绿」和完成功能目标，拙于主动保全简单性、可扩展性、少重复与少硬编码。
- 脏、乱、无结构的仓库会让后续 Agent 同样陷入「越改越碎」。
- 审阅目标包括：正确性、传播实践、可理解性、防止组织放大后的交叉项拖垮产出。

**纪律建议：**

| 做法 | 说明 |
|------|------|
| 尊重审阅带宽 | 避免「一句提示甩大 PR」；拆成可理解的变更栈 |
| 逻辑 diff + 行为轨迹 | 结合 Expect/仿真输出，让行为变化可见 |
| 区分两类「AI review」 | 全仓坏味道/风格审计（harness）≠ 驱动人类理解的 review |
| 持久化改进 | Agent 会话易忘；把结论写入 Skill、清单、门禁与文档 |
| 警惕 reward hacking | 删测试、空断言、过度 mock 换绿灯一律打回 |

自动化审计可做大规模气味扫描；**真正的 review 仍是人建立理解并裁决**。

---

## 4. 规范执行流程

1. 采集信号（线上、CI、仿真种子失败、审阅意见）
2. 止损
3. 定位层级（上表）
4. 受控修改（小步、可回滚）
5. 补齐回归（测试、属性、可重放种子、必要验证）
6. 沉淀知识（短事实、规则、Skill 更新）
7. 恢复常态观察

### 质量门禁

- [ ] 问题已止损或影响可控
- [ ] 根因层级判断明确
- [ ] 修复已完成并经过相应检查
- [ ] 回归保护已补齐（含可重放手段，若适用）
- [ ] 知识记录已更新
- [ ] 相关资产与行为保持一致
- [ ] 变更已经可理解的审阅或等价门禁

---

## 5. 简洁实例

线上偶发双写者 → 回滚止损 → 判定为协议并发缺陷 → 补模型检查与/或 DST 种子场景 → 修复实现 → 复盘写入固定回归与设计不变量说明。

---

## 6. 常见反模式

| 反模式 | 正确做法 |
|--------|----------|
| 只修症状 | 定位层级并补回归 |
| 线上直接大改 | 先止损，再受控变更 |
| 测试不更新 | 行为与资产同步演进 |
| 复盘不落地 | 结论变成规则或检查 |
| 大而不可审的 Agent PR | 拆栈、附行为轨迹、守住简单性 |
| 用删测试换绿灯 | 禁止；对齐真实契约 |
| 只做自动气味扫描当 review | 扫描辅助；理解与裁决仍要人 |

---

## 7. Agent 执行要点

1. 先问证据，再改代码
2. 修 bug 必须附带防回归手段
3. 不把所有问题都当成实现层缺陷
4. 复盘写短事实；持久化到 Skill/门禁
5. 提交变更时考虑审阅者认知负荷（粒度、说明、轨迹）

---

## 8. 本章要点

- 核心闭环：信号 → 止损 → 分层回流 → 受控修复 → 回归保护 → 知识沉淀
- 代码、验证、测试、文档必须一起演进
- Agent 时代更依赖**干净结构 + 人类理解型 review**；自动化是 harness，不是替代理解
