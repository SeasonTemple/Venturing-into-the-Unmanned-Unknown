# AI-Native SDLC · 验证（Verification）

## 1. 本章定位

验证是 AI-Native SDLC 中的核心质量环节：

**意图澄清 → 设计 → 实现 →「验证」→ 集成与交付 → 持续演进**

### 基本原则

- **风险驱动**，而非全面铺开
- **分层保证**，而非同等强度
- **可执行规格优先**：能跑的规格比纯自然语言更抗歧义
- 可自动化，可被 Agent 调用
- 结果可解释、可追溯
- 默认不启用重型定理证明（Lean/Coq 等仅用于强正确性场景）
- **接受规格无法细化到每一行实现**：锁定必须满足的性质与禁止行为，细节由实现补全并用测试快速反馈

---

## 2. 分层验证模型

| 层级 | 名称 | 目标 | 主要手段 |
|------|------|------|----------|
| L0 | 意图与表达层 | 需求清晰、低歧义 | 受控技术写作（ASD-STE100）、正反例、不变量清单 |
| L1 | 设计正确性层 | 协议 / 状态机 / 并发行为正确 | 模型检查（TLA+ / PlusCal 等） |
| L2 | 实现安全与局部正确性层 | 内存安全、溢出、断言、契约、关键不变量 | 有界模型检查、契约验证、语言级证明器、静态分析 |
| L3 | 行为符合性层 | 功能与场景符合预期 | 测试（见《测试与质量保障》章） |
| L4 | 持续保证层 | 变更不破坏已有保证 | CI 自动化 |
| L5 | 可理解性与审计层 | 结果可解释、可追溯 | 清晰文档 + 反例解释 + 差异对比 |

---

## 3. 规格歧义与 Agent 理解冲突（现实约束）

规格偏差、措辞歧义导致 Agent（人或 AI）理解冲突是常态。规格也很难细化到「实现最细的每一个决策」。

**缓解策略（工程可控，而非幻想消除）：**

1. **规格分层**
   - 高层：业务目标与不变量（可用 ASD-STE100 写清楚）
   - 中层：关键规则 + 明确边界 + 正反例表格
   - 低层：仅对真正关键路径写可执行规格（属性、契约、形式化）
2. **可执行规格优先**  
   属性测试、表格用例、简单契约，是 Agent 最不容易误解的规格形态。
3. **冲突即完善信号**  
   一旦出现理解分歧或差异测试失败，立刻把该案例反哺进规格（新性质或新表格行）。
4. **多实现交叉验证**  
   让不同 Agent / 提示生成多个实现，用差异测试暴露不一致，再裁决或以补充规格收口。
5. **接受非关键细节由实现补全**  
   规格锁定「必须成立的性质」和「禁止的行为」，而非微管理算法选型与命名。

契约式编程（Design by Contract）是把规格嵌进代码并用工具强制的一种手段；与更广义的 Spec-Driven Development（规格优先、实现服从）互补，而非对立。

## 4. 工具准备

### 按问题类型

| 问题类型 | 推荐方向 | 代表工具 | 成熟度提示 |
|----------|----------|----------|------------|
| 表达清晰、降歧义 | 受控写作 | ASD-STE100（及 Go/其他 linter） | 高（文档层） |
| 并发、分布式、状态机 | 模型检查 | TLA+ + TLC、PlusCal | 高（设计层） |
| 内存安全、溢出、UB | 有界模型检查 | Kani（Rust）、ESBMC / CBMC（C） | 依语言 |
| 函数契约与不变量 | 契约 / 证明器 | Verus、Creusot（Rust）；Frama-C（C）；**Gobra（Go，研究原型）** | Go 侧：中等，注解开销与可扩展性仍是瓶颈 |
| 功能与场景 | 测试 | 见测试章：属性测试、差异测试、变异测试等 | 高 |
| 算法强正确性（可选） | 定理证明 | Lean、Coq / Rocq | 高成本，仅关键内核 |

### 关于 Gobra（Go）

- 目前最强的 Go 形式化验证方向之一，已有 SCION border router、WireGuard 等真实案例。
- 仍属**研究原型**：SMT 性能与可扩展性不稳、注解开销约 2–3×、语言子集不完整、工业落地有限。
- **建议**：只对安全协议、资金/权限核心等**高价值模块**选择性使用；普通业务以可执行规格 + 属性/差异测试为主。

### 安装示例

```bash
npx skills add danyuchn/asd-ste100-skill
npx skills add younes-io/agent-skills --skill tla-check
npx skills add younes-io/agent-skills --skill tla-proof
# Gobra：见官方仓库与 VerifiedSCION 实践，按需引入
```

## 5. 规范执行流程

1. **意图澄清**（L0）：用受控语言 + 正反例降低歧义
2. **属性定义**：Safety / Liveness / 边界 / 契约；优先写成可执行形式
3. **设计验证**（L1）：高风险路径建模（TLA+ 等）
4. **实现验证**（L2）：按语言与风险选择有界检查、契约或 Gobra/Verus 等
5. **行为验证**（L3）：与测试章衔接
6. **持续回归**（L4）：CI 门禁
7. **解释与沉淀**（L5）：反例、差异、决策记录

### 质量门禁

- [ ] 相关属性已明确记录（含可执行部分）
- [ ] 高风险设计已验证通过
- [ ] 实现层关键检查通过（按语言与风险选工具）
- [ ] 自动化测试与 CI 通过
- [ ] 失败与反例已解释并关闭（或已反哺规格）
- [ ] 说明表达清晰、可追溯；关键规格已做低歧义处理（如 STE）

---

## 6. 模型检查（实用路径）

适合状态空间可抽象的系统：协议、权限状态机、订单生命周期、简化分布式交互。

1. **轻量**：Go/其他语言自写状态机 + BFS/DFS 或随机探索可达状态与不变量。
2. **主流**：PlusCal / TLA+ → TLC 模型检测 → 通过后再实现。
3. **成本判断**：并发交互复杂且出错代价极高时值得上；普通 CRUD 通常不划算。

---

## 7. 简洁实例

资源写锁：  
L0 用 STE/表格写清互斥与超时规则 → L1 用 TLA+ 检查协议 → L2 关键路径契约或有界检查 → L3 并发场景测试 + 差异测试 → CI 回归。

---

## 8. Agent 执行要点

1. 先澄清意图与**可执行属性**，再选工具
2. 高风险路径优先模型检查或形式化；其余用测试兜底
3. 实现层按语言现实选型（Go 上 Gobra 仅关键模块）
4. 规格冲突时优先补充可执行用例，而非加长自然语言
5. 结果必须可解释；默认不引入 Lean/Coq

---

## 9. 本章要点

- 验证是质量中枢，不是事后补充
- 分层、风险驱动；可执行规格是抗 Agent 歧义的关键杠杆
- 形式化工具（含 Gobra）有价值但有成本与成熟度边界
- 固定流程 + 自动化门禁 + 反例反哺规格
