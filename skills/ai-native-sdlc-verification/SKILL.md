# AI-Native SDLC · 验证（Verification）

验证阶段的默认基线是通过真实用户路径的运行时验证留下客观证据；在此之上，按风险分层引入可执行规格、普遍性质测试与形式化方法，并以写明“已查性质”与“未覆盖边界”的性质级证据作为门禁依据。

## 1. 阶段定位与正确性分工

本章与第 5 章（测试与质量保障）共同构成 AI-Native SDLC 的**正确性层**，一起回答“我们凭什么确信系统确实做对了”：

意图与需求 → 设计与架构 → 实现 → **「验证」** → 测试与质量保障 → 集成与交付 → 持续演进

| 维度 | 核心约定 |
|------|----------|
| 主回答的问题 | 在既定规格与环境假设下，系统的关键用户路径与核心性质是否成立、是否可被客观证伪 |
| 与第 5 章的分工 | 本章负责界定以**真实用户路径运行时验证**为核心的完成证据、性质级门禁规范以及高风险形式化验证；第 5 章负责多维行为测试、生成式输入回归与性能/资源预算核对 |
| 与瓶颈命题的关系 | 当 Agent 使得代码生成极其廉价时，缺少独立于作者的验证闭环，项目便失去了客观证明自己可交付的能力 |

### 核心原则

- **真实路径运行时证据为默认基线**：应用应当真实启动并沿完整用户操作路径运行，留下截图、录屏、状态快照或结构化日志等客观证据。
- **风险驱动、分层保证**：不把重型工具当作万能银弹，而是根据缺陷代价决定验证深度；形式化方法是分层体系中的增强层，而非每个项目的默认强制门禁。
- **可执行规格优先，普遍性质先行**：对于跨输入范围的通用不变式，优先使用属性测试（PBT）或差异测试对照，仅在状态交错或安全内核确实超出测试能力时再引入模型检查或定理证明。
- **先论证性质缺口，再决定工具选型**：绝不为了使用某种知名工具而硬套业务，调研结论本身不等于实施授权。

## 2. 分层验证模型

验证体系应当分层建设，每一层回答不同性质的问题；**某一层检查通过，绝不意味着可以替代其余层次的检验**：

| 验证层级 | 核心目标 | 典型技术手段 |
|----------|----------|--------------|
| L0 意图可判定基线 | 明确本轮要检查什么、不覆盖什么 | 意图基线、正反例与已知未知清单（第 1 章） |
| L1 端到端运行时路径验证 | 在真实环境中按用户链路走完核心场景并留痕 | 真实应用启动、端到端驱动脚本、功能地图、界面/接口状态证据 |
| L2 设计层协议与状态机验证 | 排查跨进程、多节点并发交错中的隐蔽漏洞 | 模型检查（如符合 D1–D6 准入准则时引入 TLA+、Quint、P、Alloy 等） |
| L3 实现层契约与局部证明 | 保障关键算法步进、内存安全与前后置条件 | 契约断言、有界模型检查（BMC）、静态分析与演绎证明 |
| L4 持续行为与回归验证 | 扩展边界覆盖、输入面健壮性与性能预算核对 | 属性测试、差异测试、模糊测试、Expect 轨迹与确定性仿真（第 5 章） |
| L5 门禁聚合与可审计记录 | 将零散绿灯汇总为可供人机核查的证据账本 | 性质覆盖表、未覆盖边界声明与可重放反例指针 |

### 2.1 筑牢运行时验证这一基线层

在引入任何重型数学工具之前，团队必须先把真实用户路径的运行时验证做扎实：

1. **真实启动并留存客观现场**：检查脚本必须拉起真实运行实例（或逼真的准生产沙箱），沿用户实际操作链路走完关键流程，并将结果固定为可打开审查的截图、DOM/状态对比指标、录屏或结构化运行日志；一旦失败，输出必须精准指向当时的具体状态，而非一句笼统的“等待超时”。
2. **统一路径语义与可测驱动**：为核心路径建立清晰的功能名称映射，确保人类审阅者与 Agent 使用同一套名称指代同一场景；验证驱动应当封装为可独立调用的小粒度命令，并且驱动代码本身也要具备防止假阳性的自检能力——**一条在测试历史中从未失败过的检查，往往什么也没有证明**。
3. **独立于局部单元测试**：实现者同步编写的单元测试很容易围绕“实现代码自己的理解”画圈自证，唯有走通完整链路、对真实用户可见结果负责的运行时证据，才是人工审阅的核心对象，而不是默认让人去重读每一行实现 diff。

## 3. 性质级证据与门禁记录

在 AI-Native 流程中，禁止使用“验证全部通过”这类含糊表述作为合入或发布理由。**每一项声明通过的验证检查，都必须附带以下五项性质级证据字段**：

| 字段名 | 记录内容与规范要求 |
|--------|--------------------|
| 性质 ID 与陈述 | 明确写出本次检验的是哪一条 Safety 约束、Liveness 进展条件、契约或用户路径目标 |
| 验证手段 | 说明采用的是端到端运行时驱动、属性测试、模型检查、有界模型检查还是契约证明 |
| 结果状态 | 明确标注“通过”、“发现反例（已修复/阻断）”或“在给定有界范围内通过” |
| **未覆盖边界（必填）** | 诚实列出本次检查**不作声明**的场景、参数上限、外部假设或信任边界 |
| 可重放证据指针 | 给出可直接复现运行的命令、报告路径、截图目录或确定性种子编号 |

明确的“未覆盖边界”是防止虚假安全感的关键防线，它告诉后续审阅者（HITL）究竟还剩哪些残余风险需要人工评估或通过其他层检查补齐。

## 4. 形式化验证方法与适用边界

形式化验证是指利用严谨的数学与逻辑推理手段，在给定形式化规格与模型假设下，对系统设计模型或关键实现进行穷尽性搜索或演绎证明，其产物是确定的证明结论或精确的违例反例路径，而非单次抽样运行结果。

| 方法类别 | 核心机制 | 代表性工具方向 |
|----------|----------|----------------|
| 模型检查（Model Checking） | 在给定有限状态空间内系统性搜索违反性质的执行路径 | TLA+ / TLC、Apalache、Quint、PlusCal、P、Alloy、Spin |
| 有界模型检查（BMC） | 将程序展开至有限步长或循环边界内，转化为求解器约束核验 | CBMC、Kani、ESBMC |
| 契约与演绎验证 | 在代码中标注 `requires` / `ensures` / `invariant`，由求解器自动或半自动证明 | Verus、Creusot、Frama-C、SPARK、Gobra |
| 交互式定理证明 | 由人工引导证明脚本完成高阶数学性质的严格机器核验 | Lean、Coq / Rocq、Isabelle |
| 执行轨迹与模型对齐（可选） | 将真实实现运行轨迹与形式化规格比对，或借助运行反馈校准由代码提炼的模型 | Quint（ITF 轨迹回放）、Specula（运行轨迹校准的 Agent 辅助 TLA+ 建模与反例复现） |

在系统验证的默认优先级排序上，推荐遵循：**真实用户路径运行时验证 → 可执行规格与属性/差异测试 →（满足准入条件时的）设计层模型检查 →（按语言生态选型的）实现层契约或 BMC → 第 5 章场景与回归补充**。

### 4.1 性质分类与不可忽略的信任边界

- **Safety（安全性）**：“坏事绝对不会发生”，例如两把锁不会在同一时刻被不同客户端同时持有，旧版本的数据写入不会覆盖新版本初始化结果。对于绝大多数工程系统，优先锁定高价值 Safety 性质是性价比最高的切入点。
- **Liveness（活性）**：“在明确的公平性与网络假设下，好事最终必然发生”，例如申请锁的请求最终能够得到响应。Liveness 必须显式写明环境公平性假设，切勿将“抽象意义上的最终完成”直接等同于业务层面的毫秒级超时 SLA。
- **有限实例与信任边界**：模型检查只在设定的有限节点数、有限轮次与故障模型内成立，**不得无条件外推至无限规模**；同时，规格本身写错需求、编译器 Bug、操作系统内核漏洞、FFI 外部调用以及硬件故障，均位于形式化证明的信任边界之外。

### 4.2 多语言验证生态成熟度参考

| 编程语言 | 契约与演绎验证生态 | BMC 与静态安全分析 | 工程选型建议 |
|----------|--------------------|--------------------|--------------|
| Rust | Verus、Creusot、Prusti | Kani | 针对可隔离的核心并发或密码学算法内核可按需评估 |
| C / C++ | Frama-C | CBMC、ESBMC | 在高安全关键嵌入式领域相对成熟，适合关键底层库 |
| Ada | SPARK | — | 工业级高保证领域的经典成熟路线 |
| Go | Gobra | 静态竞态分析（`-race`） | Gobra 仍偏研究原型，仅建议在极高价值且高度隔离的模块中审慎试点 |
| 其他通用语言 | 视具体生态而定 | 静态分析器、类型检查与有限 BMC | 若缺乏可靠证明器，应将重心放在可执行规格、PBT 与确定性仿真上 |

### 4.3 面向 Agent 协作的可执行规格与模型对齐工具

在以 Agent 协助建模、甚至从既有系统反推并发边界时，传统无类型 `TLA+` 手写建模常常同时面临“规格本身出现语法或类型幻觉”以及“模型与源码逐渐脱节”两重摩擦。工程上已有两类值得按需评估的补充工具方向：

- **`Quint`（类型化可执行规格语言）**：继承 `TLA` 的时序动作语义，但采用贴近现代编程语言的语法与静态类型系统；工具链内置模拟器（`quint run`），可对接 `Apalache` / `TLC` 做模型检查，并支持导出 `ITF`（Informal Trace Format）执行轨迹以驱动真实代码回放。静态类型与即时模拟能在提交模型检查前快速拦住 Agent 起草规格时的类型错配与语法幻觉，降低跨人机协作审阅规格的门槛。
- **`Specula`（从系统实现到形式化模型的闭环对齐）**：面向 `Go`、`Rust`、`C/C++` 等真实系统代码，通过编码 Agent 自动提炼 `TLA+` 规格与不变量，并借助真实实现运行轨迹与 `TLC` 模型检查反馈持续校准抽象忠实度（抑制 Agent 编造脱离源码的“教科书式空转模型”），再把搜出的并发违例反例映射回代码层复现。这类能力可直接缓解存量并发系统“补建模成本高”与“双头维护易漂移”的痛点，但引入仓库前依然必须严格服从下文 `D1–D6` 准入六问与明确维护负责人。

## 5. 形式化引入决策准则（D1–D6）

形式化验证是一种高投入、高维护成本的专项手段，**绝非所有项目的默认门禁**。在立项引入任何模型检查或证明器之前，团队必须完成从 D1 到 D6 的完整论证链；论证不全时，最多只能保留“局部候选评估项”，**严禁创建“全栈全面上 TLA+”或直接把前期调研报告当作实施授权**。

### 5.1 先盘点并扣除已有检查的覆盖范围

提出引入形式化验证的提议前，必须首先清点仓库里现有的可执行检查资产（属性测试、状态矩阵测试、专项功能测试、模糊测试入口等），避免以下三种常见浪费：

- 把单所有权模型或类型系统已经从结构上锁死的性质包装成“急需验证的缺口”；
- 仅仅因为系统“包含并发异步代码”或“仓库里还没有 `.tla` 文件”就盲目立项；
- 仅因一段内存代码长得像状态机，就机械地将其逐行翻译为两份同步维护的 TLA+ 模型。

真正的跨进程协作、跨存储故障恢复与非线性调度交错，在扣除了单点测试后往往确实存在盲区——是否值得引入形式化，仍需由以下六项准则给出理性回答：

### 5.2 准入必答六问（D1–D6）

| 准则 ID | 决策核心问题 | 合格回答要求 |
|---------|--------------|--------------|
| D1 | **具体性质与业务影响** | 明确指向既有的契约、验收条款与模块负责人；说清究竟哪类错误或活性失败造成的代价足以支撑额外验证成本（允许前瞻性评估，不必等出事故再补） |
| D2 | **相对既有手段的增量** | 在扣除现有端到端、PBT、状态矩阵与 Fuzz 检查后，新形式化手段多出来的穷尽搜索或证明维度究竟是什么 |
| D3 | **可验证的有限边界** | 明确状态模型中实例数、操作代次与故障类型的有界选取方式，以及环境假设与搜索终止条件 |
| D4 | **工具链可用性与长期维护** | 确认该工具能在当前仓库与 CI 环境中稳定运行、有明确的维护负责人（Owner）、结果可被团队解读，且总体投入优于直接扩展现有测试 Harness |
| D5 | **与真实实现的双向关联** | 说明模型产出的反例如何转化为实现层的可回放回归测试，以及如何防止模型规格与生产代码长期漂移（例如结合 Quint 的 ITF 轨迹回放，或借助 Specula 等工具做运行轨迹一致性校准） |
| D6 | **明确的停止与退出条件** | 规定在出现以下情况时立即止损或放弃引入：发现只是在重复已有测试性质、模型抽象过度失真、前置约束意外屏蔽了目标故障、缺乏人手维护或计算成本失控 |

### 5.3 不得单独成立的伪理由与真源归属

下列理由常见于盲目跟风，**均不得单独作为采纳形式化验证的立项依据**：

| 常见伪理由 | 工程剖析 |
|------------|----------|
| “项目里使用了异步和并发” | 常规单节点并发往往通过严格的所有权边界、结构化并发与属性矩阵即可有效验证 |
| “测试无法证明不存在 Bug” | 这是放之四海而皆准的常识命题，不能替代针对当前仓库具体性质增量的 ROI 论证 |
| “行业头部团队都在用 TLA+” | 他人经验只提供工具启发，不构成自身系统存在未覆盖协议缺口的证明 |
| “涉及复杂界面交互或仅仅因为前端状态多” | 界面视觉呈现与交互体验无法靠形式化协议模型保证，应首先依赖运行时路径与视觉/可达性检查 |
| “某种语言生态存在对应的证明器” | 工具存在不代表能在当前项目的第三方依赖、构建版本与人力成本下顺利落地 |
| “先期调研结论认为很有价值” | 技术调研的“有价值”只是候选信息，不等于经过 D1–D6 审核后的正式实施批准 |

一旦决定采纳形式化验证，产出的规格模型与证明义务属于**挂接在既有接口契约与模块负责人名下的可执行验证资产**；**绝对不允许在业务代码和契约之外，另立一套平行独立、双头维护的“第五层产品规范”**。性质变更必须走既有的意图与契约修订流程。

## 6. 规格歧义与多解消解

当由 Agent 大规模依据规格自动编写代码时，隐藏在自然语言甚至半形式化接口里的**规格歧义**往往会集中爆发：人类工程师过去凭借默契或经验默认了某条处理方式，而不同的 Agent 实例却可能沿着截然不同的理解分别给出“各自自洽”的实现，甚至双方都能通过各自的局部断言。

因此，当校验过程暴露出规格歧义或 Agent 间理解冲突时，应当将其视为常态化信号，采取以下四项消解策略：

1. **规格分层与精确下钻**：不要求外层业务需求写得像机器指令，而是在保持意图层业务语义的同时，将易引发多解的边界条件、错误码顺序和幂等语义下沉到接口契约表格或类型定义中锁死。
2. **反例与冲突反哺真源**：当验证工具产出违例反例、或人工审阅发现 Agent 钻了规格表述的空子时，不要只在实现代码里打补丁，而必须顺藤摸瓜回到上游补充一条明确的反例或边界条款。
3. **跨实现差异测试**：对于迁移改造、多端一致性或高歧义算法，保留旧系统或另一套简化参考模型作为对照基准，用随机生成的相同输入同时驱动新旧实现，通过差异测试直接定位理解分叉。
4. **显式记录隐含假设**：区分哪些是不可动摇的核心契约，哪些是“非关键实现细节”（例如局部日志格式、内部缓存淘汰策略等），避免过度微观管理非关键细节，同时把所有隐含假设记入证据包的未覆盖说明中。

## 7. 规范执行流程与质量门禁

1. **锚定待检目标**：盘点意图基线中的主用户路径、核心性质清单与尚存的“已知未知”。
2. **搭建端到端运行时基线**：确保应用能够以干净状态启动，跑通核心用户链路并产出现场证据。
3. **盘点既有校验并执行通用属性检查**：清理已有单元测试与属性/差异测试的覆盖范围，补齐局部通用不变式。
4. **按需启动形式化评估（D1–D6）**：若怀疑存在跨组件、跨节点组合交错风险，严格完成 D1–D6 评估；未达标则跳过，不强行立项。
5. **生成性质级覆盖账本**：按第 3 节格式汇总所有验证项的已查性质、未覆盖边界与可重放指针。
6. **闭环处置反例**：发现的反例或运行时失败必须在修复后转化为永久回归用例，或回流至上游修订规格与意图。

### 质量门禁

- [ ] 关键功能性质均具备唯一 ID 与无歧义陈述
- [ ] **关键用户路径具备真实的端到端运行时证据**（若属底层无界面组件等例外，须有显式签核跳过说明）
- [ ] 每一项声明通过的检查都已如实填写“已查性质”与“未覆盖边界”
- [ ] 跨进程并发或高风险协议路径已完成设计级检查，或已记录经批准的跳过理由
- [ ] 若工程中决定引入形式化验证工具，D1–D6 评估记录完整且维护负责人明确
- [ ] 已结合目标语言生态成熟度完成了必要的实现层静态分析、契约或 BMC 检查
- [ ] 所有通过与反例证据均可由他人通过记录的命令、脚本或种子一键重放
- [ ] 暴露出的反例已全部关闭，或已正式回流为意图/设计修正项

## 8. 工程实例：文档写锁的分层验证

承接第 1 章的“文档独占写锁”案例，在实际工程交付时，验证层不把全部希望寄托在单一手段上，而是按分层结构组织各自独立的证据：

1. **L1 端到端运行时路径验证**：启动真实应用与后端锁服务，模拟浏览器会话 A 打开文档并进入编辑状态，随后启动会话 B 访问同一文档。驱动断言会话 B 收到明确锁定提示且无法提交覆盖修改；会话 A 关闭退出后，会话 B 刷新页面即可成功获取写锁并保存内容。保留操作序列日志与失败状态截屏作为合入核心证据。
2. **L2 并发协议模型检查（经 D1–D6 评估按需引入）**：针对第 1 章遗留的“多机房时钟偏移导致租约过期误判”这一未知风险，在确认单机单元测试无法穷举网络分区与时钟漂移交错后（满足 D1–D2），建立精简的租约状态模型，在有限 3 个客户端与 2 轮时钟漂移边界内搜索 Safety 性质 `NoDualWriters`（任意时刻最多存在一个有效写者，以 fencing token 单调递增保证）。模型检查暴露了一个“旧主节点停顿后凭过期租约继续提交存储”的反例，由此推动设计层在存储网关处补充了 fencing token 校验。
3. **L3–L4 实现契约与回归沉淀**：将上述反例固化为集成仿真中的可重放时序测试用例，并在存储接口契约中硬性规定 token 校验前置条件。

## 9. 人机职责分工与本章小结

| 角色 | 本章主要工作 | 边界与注意事项 |
|------|--------------|----------------|
| Agent | 编写并运行可复用的端到端驱动、执行验证闭环、整理性质覆盖与未覆盖记录，并依据 D1–D6 判断是否值得提议新工具 | 不得擅自修改业务目标；工具在当前语言下不成熟时不得硬上；警惕自己编写的实现与自测之间存在共盲区 |
| 人（HITL） | 审查端到端运行现场证据、聚焦评估“未覆盖边界”中的残余风险、审批是否通过 D1–D6 引入形式化工具 | 认识到人类审阅带宽有限，“某个证明器绿灯”绝不等于业务场景全部正确，更不把前沿调研等同于立即实施令 |

### 本章小结

- 验证阶段的默认重心是用真实运行的用户路径建立客观证据；形式化验证是应对极高风险状态交错的第二层利器，而非默认前提或银弹。
- 性质级证据是门禁流通的基本单位，诚实写明“未覆盖什么”比追求表面的满屏绿灯更有工程价值。
- **先定位性质缺口，再挑选恰当工具**；任何形式化资产都必须锚定在既有契约与职责之上，防止规范分裂。
