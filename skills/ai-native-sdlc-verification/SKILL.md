# AI-Native SDLC · 验证（Verification）

## 1. 本章定位

验证是 AI-Native SDLC 中的核心质量环节：

**意图澄清 → 设计 → 实现 →「验证」→ 集成与交付 → 持续演进**

### 基本原则

- **风险驱动**，而非全面铺开
- **分层保证**，而非同等强度
- **可执行规格优先**：能跑的规格比纯自然语言更抗歧义
- **按语言与风险选工具**，不默认某一种语言或证明器
- 可自动化，可被 Agent 调用；结果可解释、可追溯
- 默认不启用重型交互式定理证明（Lean/Coq/Rocq 等仅用于强正确性内核）
- **接受规格无法细化到每一行实现**：锁定必须满足的性质与禁止行为，细节由实现补全并用测试快速反馈

---

## 2. 什么是形式化验证（Formal Verification）

**形式化验证**是用数学/逻辑方法，检查系统（设计模型或实现）是否满足形式化规格中陈述的性质。目标不是「多写几组用例」，而是在给定假设下，对性质给出**反例**或**通过/证明**一类更强结论。

### 2.1 与测试的分工

| | 测试 | 形式化验证 |
|--|------|------------|
| 问的问题 | 这些输入下行为对不对 | 在规格与假设下，性质是否总成立（或是否存在反例） |
| 典型产出 | 通过/失败用例 | 反例轨迹、证明义务、有界探索结论 |
| 成本 | 相对低，覆盖有限 | 建模/标注成本高，强度随手段变化 |
| 适用 | 广覆盖行为与回归 | 高风险协议、不变量、安全关键路径 |

二者互补：形式化验证不替代测试；测试也不替代对关键性质的更强检查。

### 2.2 常见手段（由轻到重）

| 手段 | 含义 | 典型工具方向 |
|------|------|--------------|
| **模型检查** | 在抽象状态空间中系统化搜索违反性质的路径 | TLA+/TLC、PlusCal、Alloy、Spin |
| **有界模型检查** | 在有限边界（深度/时间）内检查实现或模型 | CBMC、Kani、ESBMC 等 |
| **契约 / 演绎验证** | 前置/后置/不变量 + 自动或半自动证明器 | Verus、Creusot、Frama-C、SPARK、Gobra 等 |
| **交互式定理证明** | 人工引导的机器可检证明 | Lean、Coq/Rocq、Isabelle |

本书默认优先：**可执行规格 → 模型检查（设计）→ 按语言成熟度的契约/有界检查（实现关键路径）**；交互式定理证明仅用于强正确性内核。

### 2.3 何时值得做形式化验证

- 并发、分布式协议、权限状态机、资金/安全不变量
- 缺陷代价极高，且性质可以清晰陈述
- 团队能承担建模或注解成本，且所选语言/工具足够成熟

普通 CRUD 与易变业务规则：通常以可执行规格 + 测试为主，不必强上全量形式化。

### 2.4 Agent 时代的变化

生成代码变便宜后，**检查与理解**成为瓶颈。形式化规格与证明义务可提供机器可检反馈；成本结构可能改善，但仍须按风险启用，避免把未成熟工具链当成默认门禁。

## 3. 分层验证模型

| 层级 | 名称 | 目标 | 主要手段 |
|------|------|------|----------|
| L0 | 意图与表达层 | 需求清晰、低歧义、可判定 | 见意图章：对齐理解；短句/正反例/可执行验收；**不依赖**某一写作标准 |
| L1 | 设计正确性层 | 协议 / 状态机 / 并发行为正确 | **形式化**：模型检查（TLA+ / PlusCal 等） |
| L2 | 实现安全与局部正确性层 | 内存安全、溢出、断言、契约、关键不变量 | **形式化**：有界模型检查、契约验证、语言级证明器；及静态分析 |
| L3 | 行为符合性层 | 功能与场景符合预期 | 测试（见《测试与质量保障》章） |
| L4 | 持续保证层 | 变更不破坏已有保证 | CI 自动化 |
| L5 | 可理解性与审计层 | 结果可解释、可追溯 | 清晰文档 + 反例解释 + 差异对比 |

---

## 4. 规格歧义与 Agent 理解冲突（现实约束）

规格偏差、措辞歧义导致 Agent（人或 AI）理解冲突是常态。规格也很难细化到「实现最细的每一个决策」。

**缓解策略（工程可控，而非幻想消除）：**

1. **规格分层** — 高层目标与不变量；中层关键规则 + 边界 + 正反例表格；低层仅对关键路径写可执行规格（属性、契约、形式化）。
2. **可执行规格优先** — 属性测试、表格用例、契约，是 Agent 最不容易误解的规格形态。
3. **冲突即完善信号** — 理解分歧或差异测试失败时，立刻把案例反哺进规格。
4. **多实现交叉验证** — 不同 Agent/提示生成多个实现，用差异测试暴露不一致再裁决或补规格。
5. **接受非关键细节由实现补全** — 规格锁定必须成立的性质与禁止行为，而非微管理算法与命名。

契约式编程（Design by Contract）是把规格嵌进代码并用工具强制的一种手段；与更广义的 Spec-Driven Development（规格优先）互补，而非对立。

## 5. 工具准备（按问题类型 × 语言）

### 5.1 语言无关 / 设计层

| 问题类型 | 推荐方向 | 代表工具 |
|----------|----------|----------|
| 表达清晰、降歧义 | 意图章的写法习惯；英语场景可**可选**借鉴 STE 实用子集 | 团队模板；可选检查器（非门禁依赖） |
| 并发、分布式、状态机 | 模型检查（形式化验证） | TLA+ + TLC、PlusCal、Alloy、Spin |
| 算法强正确性（可选） | 交互式定理证明（形式化验证） | Lean、Coq/Rocq、Isabelle |

### 5.2 实现层：按语言对照（形式化相关）

| 语言 | 契约 / 证明器 | 有界模型检查 / 安全 | 成熟度与建议 |
|------|----------------|----------------------|----------------|
| **Rust** | Verus、Creusot、Prusti | Kani | 相对成熟；Verus 等已有工业/云场景实践，优先考虑关键模块 |
| **C / C++** | Frama-C（ACSL）、SPARK 思路可借鉴 | CBMC、ESBMC | 航空/汽车/安全关键长期使用，工具链成熟 |
| **Ada** | SPARK | — | 高保证领域标准选择 |
| **Go** | Gobra | — | **研究原型**：有 SCION、WireGuard 等案例，但 SMT 可扩展性、注解开销、语言覆盖仍有限；仅建议安全协议/资金等极高价值模块 |
| **其他** | 视生态而定 | 语言对应 BMC/静态分析 | 无合适证明器时，以可执行规格 + 测试 + 静态分析为主 |

**选型原则：** 正确性要求 × 工具成熟度 × 团队成本。不要为了「用上形式化验证」而在不成熟生态上硬推全量证明。

### 5.3 安装与技能示例

```bash
npx skills add younes-io/agent-skills --skill tla-check
npx skills add younes-io/agent-skills --skill tla-proof
# 语言相关证明器按项目语言单独引入（Verus / Frama-C / Gobra / SPARK 等）
# 英语 STE 检查 Skill 仅在有明确需要时可选安装，见意图章
```

## 6. 规范执行流程

1. **意图澄清**（L0）：对齐理解与可判定验收（见意图章；不强制写作标准）  
2. **属性定义**：Safety / Liveness / 边界 / 契约；优先可执行形式  
3. **设计验证**（L1）：高风险路径建模与模型检查（TLA+ 等）  
4. **实现验证**（L2）：按**语言与风险**选择有界检查、契约或证明器  
5. **行为验证**（L3）：与测试章衔接  
6. **持续回归**（L4）：CI 门禁  
7. **解释与沉淀**（L5）：反例、差异、决策记录  

### 质量门禁

- [ ] 相关属性已明确记录（含可执行部分）
- [ ] 高风险设计已验证通过（含必要的形式化检查）
- [ ] 实现层关键检查已按语言选型并完成
- [ ] 自动化测试与 CI 通过
- [ ] 失败与反例已解释并关闭（或已反哺规格）
- [ ] 说明表达清晰、可追溯；关键规格歧义已处理（手段自选）

---

## 7. 模型检查（实用路径）

适合状态空间可抽象的系统：协议、权限状态机、订单生命周期、简化分布式交互。与实现语言解耦。属于形式化验证中最常用的设计层手段之一。

1. **轻量**：在实现语言中自写状态机 + 穷举/随机探索不变量。  
2. **主流**：PlusCal / TLA+ → TLC → 通过后再编码实现。  
3. **成本判断**：并发复杂且出错代价极高时值得上；普通业务逻辑通常不划算。  

---

## 8. 简洁实例

资源写锁：  
L0 用可判定目标/验收与正反例写清互斥与超时 → L1 用 TLA+ **形式化检查**协议 → L2 按语言选 Verus/Frama-C/Gobra 等做关键路径契约或有界检查 → L3 并发场景与差异测试 → CI 回归。

---

## 9. Agent 执行要点

1. 先澄清意图与**可执行属性**，再选工具  
2. 高风险路径优先模型检查或其他形式化手段；其余用测试兜底  
3. **实现层必须按目标语言现实选型**（Rust/C/Ada 可更积极；Go 仅关键模块考虑 Gobra）  
4. 规格冲突时优先补充可执行用例，而非加长自然语言  
5. 结果必须可解释；默认不引入 Lean/Coq  

---

## 10. 本章要点

- 验证是质量中枢，不是事后补充  
- **形式化验证**是验证手段谱系中的一类（模型检查、有界检查、契约证明、定理证明），按风险启用  
- 分层、风险驱动；可执行规格是抗 Agent 歧义的关键杠杆  
- 形式化工具价值与成熟度**因语言而异**，按风险与生态选择  
- 固定流程 + 自动化门禁 + 反例反哺规格
