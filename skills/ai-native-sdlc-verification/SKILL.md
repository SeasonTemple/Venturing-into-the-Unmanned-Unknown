# AI-Native SDLC · 验证（Verification）

## 1. 范围与定位

本章属**正确性层**（与第 5 章测试共同回答「如何知道对不对」）。

**生命周期位置：** 意图 → 设计 → 实现 → **验证** → 测试衔接 → 集成交付 → 演进

| 项 | 约定 |
|----|------|
| 主问题 | 在规格与假设下，关键性质是否成立或可否证伪 |
| 与测试 | 测试覆盖场景与回归；本章覆盖更强/设计层/局部实现性质 |
| 瓶颈关系 | 生成廉价后，无独立检查则项目无法证明可交付 |

### 原则

- 风险驱动；分层保证
- 可执行规格优先
- 按语言成熟度选工具
- 结果可重复、可解释
- 默认不上重型交互式定理证明（仅强正确性内核）
- 接受规格无法穷尽每行实现
- **先证明性质缺口与增量，再选工具**；调研结论不得直接当作实施授权

---

## 2. 性质级证据（门禁字段）

每条通过的检查**必须**可填写：

| 字段 | 含义 |
|------|------|
| 性质 ID / 陈述 | 检查的是哪条 Safety/Liveness/契约/不变量 |
| 手段 | 模型检查 / BMC / 证明器 / 静态分析等 |
| 结果 | 通过 / 反例 / 有界内通过 |
| **未覆盖** | 本检查**不**声称的内容（明确写出） |
| 证据指针 | 日志、命令、报告路径或可重放脚本 |

禁止仅用「验证通过」作为晋级理由。绿灯只证明已声明的性质。

---

## 3. 形式化验证

用数学/逻辑方法检查模型或实现是否满足形式化规格中的性质。产出为反例或通过/证明类结论，而非单组用例。

| 手段 | 含义 | 代表方向 |
|------|------|----------|
| 模型检查 | 状态空间搜索违反性质的路径 | TLA+/TLC、P、PlusCal、Alloy、Spin |
| 有界模型检查 | 有限边界内检查 | CBMC、Kani、ESBMC |
| 契约 / 演绎验证 | requires/ensures/invariant + 证明器 | Verus、Creusot、Frama-C、SPARK、Gobra |
| 交互式定理证明 | 人工引导证明 | Lean、Coq/Rocq、Isabelle |
| Trace / 观测对照 | 实现轨迹与规格/monitor 对照 | 可选；非零成本附赠 |

默认优先级：可执行规格与现有测试 → 设计层模型检查（有缺口时）→ 实现层契约/BMC（按语言）→ 测试章补场景与回归。

### 3.1 Safety、Liveness 与证明边界

| 概念 | 说明 |
|------|------|
| Safety | 「坏事不发生」（如旧结果不得覆盖新初始化） |
| Liveness | 「在明确假设下好事最终发生」；须写环境/公平性假设 |
| 有限实例 | 模型检查在所选常量与约束内成立，不得无条件外推无限规模 |
| 信任边界 | 规格错误、编译器、OS、FFI、硬件仍可能在证明范围之外 |

只验证高价值 safety 合理；不必每个模型都附加 liveness。业务时限 ≠ 抽象「最终完成」。

### 语言与成熟度（摘要）

| 语言 | 契约/证明 | BMC/安全 | 建议 |
|------|-----------|----------|------|
| Rust | Verus、Creusot、Prusti | Kani | 可隔离关键内核可评估 |
| C/C++ | Frama-C | CBMC、ESBMC | 安全关键成熟 |
| Ada | SPARK | — | 高保证领域 |
| Go | Gobra | — | 研究原型；仅极高价值、可隔离模块 |
| 其他 | 视生态 | 静态分析/BMC | 无证明器则规格+测试为主 |

## 4. 形式化引入决策（规范性）

形式化是手段谱系中的一类，**不是默认门禁**。采纳前须建立证据链；缺链则保持「保留候选 / 不引入」，不得将调研报告当作实施授权。

### 4.1 采纳前必须回答

| ID | 问题 |
|----|------|
| D1 | **具体性质与影响**：指向契约/验收/owner；何种错误或进展失败值得额外成本（可前瞻，不必先等事故） |
| D2 | **相对增量**：现有 BDD/PBT/矩阵/fuzz/调度/变异已覆盖什么；新方法多出的搜索或证明维度是什么 |
| D3 | **可验证边界**：有限 actor/代次/故障如何选；环境假设；是否查 liveness；搜索完成条件 |
| D4 | **可运行与可维护**：工具链在本语言/平台可用；维护 owner；运行入口；结果解读；成本与扩展现有 harness 的比较 |
| D5 | **实现关联**：反例如何变成可回放回归；如何防止模型与契约/代码漂移（trace 对照可选） |
| D6 | **停止条件**：仅重复已有性质、抽象失真、约束吃掉目标故障、无人维护或成本超范围 → 不采纳或终止评估 |

未完成 D1–D6 时：**不得**创建「全面引入形式化 / 全栈上 TLA+」类实施项；至多保留限定性质的候选评估项。

### 4.2 先扣除已有检查

提出候选前**必须**列出已有可执行断言（PBT、状态矩阵、专项 FT、fuzz 入口等），避免：

- 把单 owner / 内存模型已覆盖的性质包装成新缺口
- 把「有并发」「仓库里没有 .tla」当成充分理由
- 为「代码写得像状态机」而机械翻译一份模型并双维护

跨进程、跨 owner、跨存储与调度的**组合交错**，在扣除单点检查后仍可能构成观察点；是否值得系统探索，仍须用 D2/D4 论证。

### 4.3 伪理由（不得单独作为采纳依据）

| 伪理由 | 说明 |
|--------|------|
| 有并发 / 有异步 | 现有 PBT 与矩阵可能已覆盖关键语义 |
| 测试不能证明一切 | 普遍命题，不替代本项目增量论证 |
| 行业用过 TLA+ | 启发组合实践，不是本仓 ROI |
| UI 二字 | 既不自动排除协议模型，也不自动值得上；视觉/无障碍不是模型通过能保证的 |
| 工具名存在于生态 | 须验证语言版本、平台、库与维护成本 |
| 调研结论「有价值」 | 价值 ≠ 已证明缺口与可维护实施路径 |

### 4.4 与规格真源的关系

若采纳：模型与证明义务是**可执行验证资产**，挂在既有契约/owner 下；**不得**另立与契约并列的独立产品规范层。性质变更走既有意图/契约流程，不因换工具重写领域职责。

### 4.5 候选形态（若保留）

限定：性质 ID、主 owner、与现有测试的差别、拟比较的方法（不预先锁死单一工具）、假设与停止条件。候选评估 ≠ 已接受设计 ≠ 实施授权。

## 5. 分层模型

| 层 | 目标 | 手段 |
|----|------|------|
| L0 | 意图可判定 | 见意图章 |
| L1 | 设计协议/状态机 | 模型检查（有 D1–D6 时） |
| L2 | 实现局部正确与安全 | 契约、BMC、静态分析 |
| L3 | 行为符合性 | 第 5 章测试 |
| L4 | 持续保证 | CI |
| L5 | 可审计 | 反例解释、性质覆盖表 |

---

## 6. 规格歧义

歧义与 Agent 冲突为常态。策略：规格分层；可执行优先；冲突反哺；差异测试；非关键细节不微管理。

---

## 7. 流程与门禁

1. 确认意图中的属性与已知未知  
2. 定义可执行性质；盘点已有测试/检查  
3. 若考虑形式化：完成第 4 节 D1–D6；否则跳过  
4. L1/L2 按风险与成熟度执行  
5. 性质覆盖表交给测试章与交付门禁  
6. 反例关闭或回流规格  

### 质量门禁

- [ ] 关键性质有 ID 与陈述（可执行优先）
- [ ] 每条通过检查填写「已查性质」与「未覆盖」
- [ ] 高风险设计检查已完成或显式签核跳过
- [ ] 若引入形式化工具：D1–D6 已记录；维护 owner 明确
- [ ] 实现层检查按语言成熟度选型并完成
- [ ] 证据可重放（命令/报告/脚本）
- [ ] 反例已关闭或已建回流项

---

## 8. 对 Agent / 对 HITL

| 受众 | 帮助 | 局限 |
|------|------|------|
| Agent | 可跑检查闭环；按 D1–D6 判断是否提议新工具 | 不选择业务目标；工具不成熟时不得硬闯；自测同源可能共错 |
| HITL | 聚焦未覆盖性质、反例与引入决策记录 | 带宽有限；「证明器绿了」≠ 业务正确；不把调研当实施令 |

---

## 9. 要点

- 验证与测试同属正确性层；本章偏性质与更强保证
- 性质级证据是门禁单位
- 形式化按风险、增量与可维护性启用；**先性质后工具**
