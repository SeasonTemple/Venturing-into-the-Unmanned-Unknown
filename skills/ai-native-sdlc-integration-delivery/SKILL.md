# AI-Native SDLC · 集成与交付

集成与交付阶段将经过正确性层检验且附带性能核对结果的变更，转化为可追溯、可审计、可随时回滚的发布版本；门禁规则从基线读取且不可被待合入变更私自放宽，人类裁决聚焦于完整证据包与残余风险。

## 1. 阶段定位与交付硬约束

集成与交付连接研发内部闭环与真实运行环境，是把“局部代码正确”升级为“组织级可上线承诺”的最后关卡：

**意图与需求 → 设计与架构 → 实现 → 验证与测试 →「集成与交付」→ 持续演进**

**不可逾越的交付硬约束**：凡是缺乏性质级正确性证据的变更，**不得进入发布流程**；凡是设计与意图阶段**已经承诺**的性能或资源预算指标未通过核对（且未经 HITL 正式签核延期豁免）的版本，**严禁上线发布**。

---

## 2. 四级门禁体系与门禁治理

按反馈速度与成本差异，集成与交付阶段的门禁分为四个递进层级：

| 门禁级别 | 核心校验内容 | 失败时的处置动作 |
|----------|--------------|------------------|
| 提交级（Commit） | 代码格式、Lint 静态检查、类型校验与快速局部单元测试 | 立即阻断合并请求或本地提交推进 |
| 合并级（Merge） | 完整回归测试、真实用户路径端到端验证、构建验证及性质覆盖汇总表 | 阻断合入主干分支 |
| 发布级（Release） | 发布冒烟校验、数据结构迁移演练、已承诺性能/资源预算核对与制品签名追溯 | 阻断部署进入生产环境 |
| 运行级（Runtime） | 线上可用性健康探针、核心业务错误率与关键资源预算指标实时监控 | 自动触发止损、熔断降级或版本回滚 |

所有的合并请求与发布说明，必须能够清晰回答两项核心问题：**功能性质覆盖了哪些、尚未覆盖哪些**，以及**已承诺的性能与资源预算是否在标明环境的基线上核对通过**。

### 2.1 三项关键门禁治理原则

1. **守护门禁的基线不可变性**：用于守卫本次变更的门禁脚本、规则配置与验收基线，必须从受保护的主干基线读取，**严禁由待合入的本次变更自行改写**。开发者或 Agent 可以在变更中**新增**更严格的检查，但绝不允许在同一个改动中修改、删减或放宽刚好拦住自己的那一条检查。
2. **新门禁先观察、后阻断**：任何新引入的检查规则或静态约束，在全面强制阻断之前，应当先以“只记录违例、不阻塞合入”的观察模式运行一段时间，确认误报率可控且修复路径明确后，再正式切换为硬性阻断门禁。
3. **自动修复设置熔断上限**：当 Agent 针对同一条门禁红灯连续尝试修复两至三轮仍无法通过时，必须立刻停止继续盲目改写代码，并将完整错误现场交由人类（HITL）诊断根因，防止陷入拆东墙补西墙的无限重试循环。

## 3. 结构化证据包与 Agent 合入纪律

在代码生成量大幅增长的团队里，要求人类审阅者逐行核对庞大变更集中的所有代码细节既不现实、也往往流于形式。因此，AI-Native 交付提倡**“以结构化证据包为核心、按需下钻代码关键点”的审阅范式**。

每次合并或发布提交都必须附带一个**可直接打开查验的证据包**，内容包括：本次实际跑通的用户路径说明、客观现场产物（运行截图、终端日志或行为轨迹对比）、已检验的性质列表、明确列出的未覆盖边界、性能基线对比数据以及可执行的回滚方案。人工审阅首先验证这些证据是否完整可信，而非机械地重读每一行 diff。

同时，Agent 在提交合入请求时必须严守以下纪律：

- **小批量与可逐层审阅的变更栈**：将复杂任务拆分为职责单一、易于独立检验与理解的小型提交或堆叠式变更（Stacked PRs），控制单次变更对 HITL 造成的认知负荷。
- **完整声明来源与上下文**：合入说明必须关联对应的意图基线与接口契约指针、性质级覆盖摘要、预算结果（或显式“未承诺”说明）及变更回滚路径。
- **零容忍违规绕过**：严格禁止通过删除或注释既有测试用例、编造空断言、拉长超时阈值或篡改基线数据来强行换取流水线绿灯；一经自动审计或人工发现，直接打回并触发问题回流。

## 4. 规范执行流程与质量门禁

1. **准备集成与证据包**：划定清晰的合入范围，集齐端到端运行证据、性质覆盖表、数据库/配置迁移脚本及验证过的回滚预案。
2. **组织小批量合入**：按功能边界拆分为可独立审查与回滚的小粒度变更单元。
3. **通过合并级基线门禁**：确保从基线读取的自动化检查全部通过，未包含任何放宽自身校验规则的越权改动。
4. **完成发布前综合审核**：核对已承诺的性能与资源指标、未覆盖边界中的残余风险，必要时由 HITL 明确签核。
5. **分阶段灰度推进**：通过金丝雀或分批次发布逐步放量，同步紧盯运行级健康与预算监控信号。
6. **确认交付完成或执行回滚**：运行平稳且指标符合预期则完成交付并沉淀记录；一旦触及异常阈值，立即执行预设回滚方案止损，并将线索移交第 7 章持续演进。

### 质量门禁

- [ ] 从基线读取的自动化提交级与合并级检查全部通过
- [ ] **结构化证据包完整且可直接打开查验**；本次变更未修改或放宽拦住自己的既有检查规则
- [ ] 性质级覆盖表齐全，已查性质与未覆盖边界表述清晰无含糊
- [ ] 已承诺的性能与资源预算门禁全部通过，或持有经过正式批准的书面延期记录
- [ ] 未在无充分理由与授权的情况下跳过关键回归测试
- [ ] 发布制品与构建版本、源码提交一一可追溯，且回滚方案经验证可用
- [ ] 高风险发布或涉及显式未覆盖边界的变更，已获得 HITL 人工裁决通过或符合预设书面审批策略

## 5. 人机职责分工与本章小结

| 角色 | 本章主要工作 | 边界与注意事项 |
|------|--------------|----------------|
| Agent | 按小批量原则提交变更、组装可打开的证据包、在基线门禁内排查修复，连续多轮未过时及时上报 | 不得自行决定放行存在高残余风险的发布，也不得修改保护主干的检查配置来为自己开绿灯 |
| 人（HITL） | 查验证据包中的真实运行效果与“未覆盖边界”，核准性能延期与高风险发布，决定何时加严自动门禁 | 当变更提交速度超出人工审阅承受上限时，应优先停下来收紧自动门禁与拆小批次，而不是草率放行 |

### 本章小结

- 集成与交付阶段通过**不可私自篡改的基线门禁**与**可打开查验的结构化证据包**，把局部的正确性证据转化为组织级的可控发布承诺。
- 在这一闭环中，Agent 负责规范推进与自检举证，系统门禁行使客观否决权，而人类（HITL）则牢牢把握残余风险与最终发布责任。
