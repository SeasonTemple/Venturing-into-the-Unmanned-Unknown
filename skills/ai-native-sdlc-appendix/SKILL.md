# AI-Native SDLC · 附录

附录汇总全书跨生命周期的核心硬性门禁清单、关键增补术语、常见工程反模式对照表，以及当前版本方法论的已知局限与尚待探索的开放问题，便于团队与 Agent 在评审、交付和复盘前快速核对。

## 1. 全流程核心门禁摘要

全流程的完整逐项检查表维护于 `checklists/master-checklist.md`。其中，跨阶段必须严格遵守的核心硬性门禁如下：

- [ ] **意图可判定且诚实留白**：当前迭代的目标与端到端完成路径清晰可判定，暂不明确的条件已如实标注为“已知未知”
- [ ] **结构防错与基线对齐**：已知的高频易错点已通过目录边界、类型约束或静态检查阻断，重复出现的审阅纠正已转化为自动化检查
- [ ] **关键性质具备唯一标识**：所有核心安全约束、性能预算与验收条款均拥有可追踪的性质或指标 ID
- [ ] **端到端证据界定完成**：关键用户路径具备真实环境运行的客观证据（而非仅凭局部单元测试绿灯替代），例外豁免持有显式签核
- [ ] **性质级覆盖显式可审计**：每一项通过声明均如实写明“已查性质”与“未覆盖边界”，证据可一键重放
- [ ] **形式化引入经过严格论证**：若采用模型检查或定理证明工具，必须已完成第 4 章 D1–D6 准入评估且明确维护负责人
- [ ] **基线门禁不可被待合入变更篡改**：待合入变更必须通过主干基线门禁的检验，严禁在自身改动中放宽或删减拦住自己的检查

## 2. 关键术语增补

除第 0 章（导论）已经界定的基本术语外，本书在后续各章中使用的关键工程术语统一约定如下：

| 术语 | 精确工程含义 |
|------|--------------|
| 正确性层 | 由第 4 章（验证）与第 5 章（测试与质量保障）共同组成的校验层级，系统性地回答“凭什么相信产物正确” |
| 性质级证据 | 同时陈述“检查了哪条具体性质或预算”“使用何种手段”“哪些边界条件仍未覆盖”以及“如何重放查验”的结构化门禁证据 |
| 验证闭环 | Agent 作出修改后主动运行独立于自身的检查工具、解析客观失败现场并迭代修正，直至满足门禁条件或触及熔断上限的循环 |
| 同源共错 | 当实现代码与对应测试同由 Agent 基于同一份理解生成时，测试恰巧复制了实现里的错误假设，导致测试全绿但产品路径失效的现象 |
| 认知投降 | 当面对大量快速生成的改动或复杂证明报告时，人类审阅者放弃独立判断与抽查验证，直接将 Agent 的结论当作可靠结论放行的失效模式 |
| 编排税 | Agent 生成代码与提交变更的速度持续超过人类（HITL）能够负责任地理解并做出高质量审阅的吞吐上限时，所积累的风险与协调缺口 |
| 形式化引入决策 | 在立项采纳模型检查、有界检查或演绎证明器之前，必须依次完成性质影响（D1）、增量评估（D2）、有限边界（D3）、维护可行性（D4）、实现关联（D5）与停止条件（D6）论证的规范流程 |

关于生产主体、HITL、系统保证与确定性仿真（DST）等基础概念，以第 0 章导论为准。

## 3. 高频工程反模式对照

以下汇总了在实践 AI-Native SDLC 过程中最易出现的工程误区及其修正做法：

| 高频反模式 | 根源剖析与正确的工程做法 |
|------------|--------------------------|
| 仅凭“CI 一片绿灯”即放行发布 | 绿灯只证明已有脚本未报错；必须汇总性质级覆盖表并显式审阅“未覆盖边界” |
| 用同一 Agent 自写自测作为唯一正确性证据 | 同源自证极易形成共盲区；必须依托真实端到端路径、独立规格、差异对照或局部变异检查打破闭环 |
| 只顾扩容 Agent 并发产出，却不升级检查与门禁 | 缺乏门禁护栏的并发扩产只会加速积累垃圾与冲突；应先收紧结构防错与自动门禁，再控制变更粒度与合并批次 |
| 对 Agent 提交的改动或证明结论产生认知投降 | 人类必须坚持基于端到端现场证据与关键假设进行抽查核实，无法辩护其安全性时坚决拒绝合并 |
| 把验证章与测试章割裂成互不关联的两套流程 | 二者同属正确性层：验证确立端到端运行时基线与强性质证明，测试补齐回归网、随机生成输入与预算核对，共守同一套性质 ID |
| 未扣除已有属性测试与状态矩阵覆盖就盲目开立形式化任务 | 提出形式化候选前必须先清点并扣除已有可执行断言，明确阐述在跨进程或组合状态空间上的真实增量 |
| 先选定某个时髦工具名，再去业务里强行找适用场景 | 坚持“先定位性质缺口，再评估工具”，禁止为使用某个框架或证明器而扭曲工程重点 |
| 把技术调研报告直接当作立项实施授权 | 候选评估与工程立项必须严格分阶段；缺 D1–D6 完整论证链时一律保持候选状态，不予立项 |
| 仅因代码长得像状态机就机械翻译出独立 TLA+ 并双头维护 | 若无法论证不可替代的并发增量且无人负责长期同步维护，则不应机械翻译双份资产 |
| 在契约与代码之外另立“第五层产品规范” | 所有形式化模型与证明义务都是可执行验证资产，必须挂接在既有接口契约与模块负责人名下 |
| 用自然语言规则文档或代码注释代替结构约束与 Lint | 规则文档被忽略时不会阻断构建；凡是重复出现两次以上且可识别的问题，应直接通过目录、类型或静态检查禁止其写出 |
| 用局部单元测试全绿代替完整产品的真实运行检验 | 功能完成必须由真实用户路径的端到端运行证据界定，单元测试仅负责保护局部逻辑回归速度 |
| 把形式化方法当作默认门禁或万能银弹 | 默认基线是跑通真实用户路径并留存证据；形式化仅按 D1–D6 风险准入，且依然必须声明其信任边界外的未覆盖项 |
| 将耗时巨大的全量变异测试强塞进日常开发内环 | 变异测试只衡量测试断言有效性且计算高昂，应严格限定于本次改动代码、设好时间与数量预算放在提交前运行，未跑完部分标为未覆盖 |
| 允许待合入变更修改刚好拦截住自己的测试或门禁规则 | 守卫变更的检查基准必须从主干基线读取；本次改动只可新增检查，绝不允许放宽或删改既有拦截规则 |

## 4. 方法局限、开放问题与版本说明

### 4.1 适用边界与方法局限

- 本书提供的是工程生命周期骨架，**不能直接替代**医疗、航空、汽车电子或金融监管等特定行业所要求的法定合规认证或执业签字流程。
- 形式化验证与全系统确定性仿真（DST）受目标编程语言生态成熟度及算力、人力成本的严格约束，决不能将其当作无条件普适开关。
- 截至当前版本，本书所提倡的各项实践尚缺乏跨行业大规模长期双盲对照实验提供的量化因果证明。
- 本书专注于软件研发与质量工程过程本身，不涉及企业人员招聘、法务合同责任划分或组织内部预算政治等管理议题。

### 4.2 尚待探索的开放问题

- 随着基础模型推理与长程工具调用能力持续跃迁，人类在环内（HITL）不可替代的“最小必要裁决集”应如何动态迁移？
- 在数十个 Agent 长期并行演进超大型单体仓库时，规格所有权归属与自动冲突消解协议如何做到低摩擦且零静默覆盖？
- 当连端到端测试、属性断言甚至形式化模型本身也由 Agent 起草生成时，如何在工程制度层面从根本上保证校验视角的真正独立性？

### 4.3 当前版本演进中的不足（v0.0.5）

- 性质覆盖表与证据包的机器可读交换 Schema 尚未在本仓中统一标准化，目前仍以结构化表格和约定字段为主。
- 各章示例主要围绕通用后端服务与交互式站点场景展开，尚未提供覆盖嵌入式硬件驱动、深度学习训练流水线等特种领域的专项样本。
- 仓库静态检查脚本与在线阅读站点在特定开发分支合并前，仍需人工触发完整构建校验以防内容同步滞后。

### 4.4 本书结构与版本演进说明（v0.0.5）

当前版本的全书阅读与执行顺序为：**导论（第 0 章）→ 意图与需求（第 1 章）→ 设计与架构（第 2 章）→ 实现（第 3 章）→ 验证（第 4 章）→ 测试与质量保障（第 5 章）→ 集成与交付（第 6 章）→ 持续演进（第 7 章）→ 工具与技能生态（第 8 章）→ 附录**。

其中，第 4 章与第 5 章紧随实现阶段之后、交付阶段之前共同构成**正确性层**：验证以真实用户路径的运行时证据为默认基线，形式化作为按风险启用的第二层增强手段，测试则负责多维行为回归网与已承诺性能预算核对。

## 5. Agent 检索与执行指引

1. **按环节就近检索清单**：遇到具体阶段的推进犹豫或门禁缺失时，直接加载对应章节的 Skill 文档展开执行与自检。
2. **术语冲突仲裁基准**：当不同文档或外部资料对角色、门禁或证据概念表述不一致时，一律以本附录与第 0 章导论的界定为准。
3. **坚持主体分工与遇阻即停**：Agent 始终承担默认生产与验证闭环推进职责，但在硬门禁失败、超过熔断重试上限或触及未覆盖高风险边界时必须立刻停止并升级至 HITL。
4. **审慎响应形式化咨询**：当用户询问“该项目是否应该引入 TLA+、Kani 或形式化证明”时，严格引导其按照第 4 章第 5 节的 D1–D6 准入六问逐项评估，严禁脱离性质缺口空泛堆砌工具名称。
