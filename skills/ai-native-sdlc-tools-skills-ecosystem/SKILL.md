# AI-Native SDLC · 工具与技能生态

工具与技能建设必须遵循自底向上的工程顺序：优先利用目录结构、类型约束与可重复运行的自动化检查固化确定性边界，再将可复用命令接入持续集成流水线，最后才用边界清晰的技能（Skill）来承载上下文判断与流程编排。

## 1. 阶段定位与选型原则

本章作为横跨全书各生命周期阶段的支撑层，回答如何高效组织 CLI 工具、验证与仿真器、MCP 连接器、CI 门禁以及 Agent Skill，使整套工程方法论能够稳定、低摩擦地落地运行。

### 基本原则

- **以阶段完成标准反推选型**：工具服务于“产出可信证据、阻断低级错误”，不盲目堆砌流行插件或追求大而全的配置。
- **先通用基座，后按需重器**：优先夯实通用构建、Lint 与端到端驱动；形式化验证、模糊测试与全系统仿真等重型工具严格**按风险与目标语言成熟度启用**。
- **脚本化与命令行优先**：具备纯 CLI 入口和结构化输出（如 JSON 报告与明确退出码）的工具，既便于 Agent 闭环调用，也能在本地与 CI 中复现一致结果。
- **技能定义必须写清边界**：任何 Skill 都应明确其触发场景、输入依赖与能力边界，避免模糊描述导致错误路由。
- **权限最小化与过程可审计**：严格收紧写入权限与外部调用边界，防止未受控脚本污染环境或绕过门禁。
- **保持技术栈中立**：方法论约束的职责固定不变，具体选用的编辑器、模型检查器、仿真平台或 CI 产品可随时替换。

## 2. 能力分层与建设优先级

团队在搭建 AI-Native 研发基础设施时，最容易犯的错误是**把建设顺序搞反**：在目录混杂、缺少静态检查和自动化测试的情况下，急着撰写大量自然语言规则文件或复杂的编排型 Skill。然而，**当内环生产出来的本身就是未经验证的缺陷产物时，用技能去加速自动化只会以更快的速度批量制造缺陷**。

| 能力层级 | 载体形态 | 核心定位与职责 |
|----------|----------|----------------|
| L5 流水线自动化 | CI / Git Hooks | 在提交、合并与发布边界强制执行统一的检查路径并守卫基线门禁 |
| L4 外部能力连接 | MCP / Plugin | 受控连接问题追踪、代码库检索、监控告警或特定外部专业系统 |
| L3 验证与仿真层 | 运行时驱动、模型检查、BMC、契约与 DST | 提供真实用户路径运行证据、协议状态搜索及可控故障仿真 |
| L2 基础工程执行 | CLI / SDK | 承担构建打包、静态 Lint、类型检查、常规测试与部署回滚命令 |
| L1 流程与判断层 | Skill / 工程规则 | **最后一层**：仅承载那些无法被工具或目录结构硬性替代的上下文取舍、触发条件与审阅判断 |

**正确的四步建设顺序**：

1. **先通过结构与静态检查让错误写不出来**：梳理模块目录隔离、导入依赖检查、强类型定义与基础 Lint。
2. **再把关键验证封装成可重复运行的独立命令**：打通端到端运行时路径检查与常规回归测试脚本。
3. **接着接入 CI 与本地一致的强制门禁**：确保本地能跑的检查即线上门禁，防止“本地过而 CI 挂”或私自绕过。
4. **最后编写精准简洁的 Skill 承载流程判断**：将无法编码为静态检查的工程权衡与多步协作流程写入 Skill。

### 2.1 可复用运行时验证技能（Harness）的五项设计要求

每当团队将一条核心用户路径或端到端检查沉淀为可被 Agent 重复调用的验证脚本或 Skill 时，该验证驱动必须固定包含以下五项机制：

1. **从干净可控的状态启动并明确“真正可用”的就绪标准**：清理陈旧状态或使用隔离临时目录，在真正发送操作前探测服务端口或关键界面元素就绪，而非写死盲等时间。
2. **先做一次只读的基线体检**：在执行写操作或破坏性模拟前，先核查前置条件、静态资源或初始环境处于预期基线。
3. **严格沿着真实用户路径驱动**：从用户的实际交互入口触发流程，而不是偷偷走内部后门接口替代业务链路。
4. **产出的证据能够存留到清理之后**：把截图、DOM 指标、运行日志与失败现场写入独立的证据输出目录，确保临时进程清理后人类审阅者依然可以打开查看。
5. **只终止本次拉起的专属进程树**：通过精确记录自身拉起的子进程 PID 或隔离配置清理资源，绝不误杀宿主机上用户正在使用的其他浏览器或服务实例。

## 3. 各环节最小工具集与选型参考

在项目冷启动或轻量团队中，每个生命周期阶段只需配置下表所示的最小核心工具集，即可顺畅跑通全书闭环：

| 研发环节 | 最小工具与载体需求 |
|----------|--------------------|
| 意图与需求 | 结构化的目标 / 非目标 / 验收 / 已知未知模板（如 `templates/intent-template.md`）；消歧以“人机理解一致、结果可判定”为准，不强绑定特定受控写作检查器 |
| 设计与架构 | 模块边界/依赖检查脚本、接口契约与 ADR 模板；存在跨节点协议高风险时按需配置模型检查入口 |
| 实现 | 目标语言标准构建工具链、格式化工具、Linter 与严格类型检查器 |
| 验证 | 可重复执行的端到端运行时驱动与证据收集脚本；经 D1–D6 评估确有需要时，按语言生态叠加模型检查或契约证明工具 |
| 测试与质量 | 自动化测试框架（单元 / 表驱动）与属性测试库；按项目需要选配 Fuzz、差异比对、Expect 快照或可插拔确定性仿真（DST）运行时 |
| 集成与交付 | 构建、迁移验证与回滚脚本，以及从基线读取配置并汇总性质覆盖表的 CI 门禁流水线 |
| 持续演进 | 结构化日志与性能指标采集告警、复盘记录模板及可重放故障种子归档目录 |

### 3.1 验证工具中立选型提示与按需扩展命令

- **设计协议层（语言无关）**：`TLA+` / `PlusCal`、`P` 或 `Alloy` 等适合在编码前或并发重构时排查协议交错隐患。
- **实现验证层（随语言生态成熟度而定）**：Rust 可关注 `Kani` / `Verus` / `Creusot`；C/C++ 可依托 `CBMC` / `Frama-C`；高安全领域可使用 `Ada SPARK`；Go 等证明器仍在演进中的语言应将重点放在竞态检测、清晰边界与仿真测试上。
- **表达与受控写作辅助**：仅当英文文档歧义已造成明显返工成本时，才可作为可选项安装英文受控写作辅助 Skill，切勿列入必需最小工具集。

以下为按需安装专项增强 Skill 的可选参考命令（仅在经风险评估确需启用时执行）：

```bash
npx skills add younes-io/agent-skills --skill tla-check
npx skills add younes-io/agent-skills --skill tla-proof
```

## 4. 规范执行流程与质量门禁

1. **梳理业务链路与核心风险点**：明确当前系统最容易失守的边界、易错模式与高代价故障面。
2. **搭建并加固最小工程基座**：优先完善目录隔离、静态检查与可重复的构建测试命令。
3. **构建端到端驱动与性质验证入口**：落地第 2.1 节规定的五步运行时验证机制，并打通本地与 CI 的统一调用面。
4. **按需沉淀高内聚判断型 Skill**：将稳定、高频的跨步流程与触发边界写入 Skill，控制技能总量，避免同名异义的重叠技能相互冲突。
5. **在真实变更中试运行并持续裁剪**：通过真实开发任务检验工具链的实际拦截效果，定期下线长期闲置、收益低或造成不必要阻塞的冗余工具与规则。

### 质量门禁

- [ ] 每个关键生命周期环节均已配备至少一种可自动执行的最小工具手段
- [ ] 本地开发运行路径与 CI 门禁流水线调用的是同一套检查命令与配置基准
- [ ] 核心 Agent Skill 均写明了清晰的触发条件、输入依赖与适用边界，且能准确路由生效
- [ ] 工具调用与外部 MCP 服务均已落实最小权限控制，失败时能够返回可读的错误原因
- [ ] 不存在大量长期无人使用、职责重叠的冗余技能或僵尸脚本
- [ ] 形式化验证、全系统仿真等重型工具已设定明确启用条件，而非无差别默认全开
- [ ] 文本写作风格类辅助检查器未在未经团队显式决议的情况下被设为阻断合入的硬门禁

## 5. 人机职责分工与本章小结

| 角色 | 本章主要工作 | 边界与注意事项 |
|------|--------------|----------------|
| Agent | 依据当前任务所属阶段与风险级别选用最小对应工具，遇到工具故障时输出明确可解释的诊断信息 | 严禁擅自无限扩装外部技能或未经许可修改流水线权限；同一工程目的只保留一条清晰主路径 |
| 人（HITL） | 审批重型工具与外部连接器的引入、把控最小权限边界、主导定期工具与技能的精简审计 | 避免陷入“配置工具越多越安全”的幻觉，持续推动将反复需要的判断收敛成简洁可靠的静态与运行时检查 |

### 本章小结

- **Skill 是判断与编排层，而不是工程地基**；凡是能固化为目录结构、静态类型、Lint 规则或可重复运行时检查的约束，就不应只留在自然语言规则里。
- 以每个环节的完成标准反推最小工具集，坚持小而稳、可审计、本地与 CI 同源的工具链架构，远胜于盲目堆砌重型生态。
