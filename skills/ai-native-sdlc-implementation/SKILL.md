# AI-Native SDLC · 实现（Implementation）

实现阶段由 Agent 依照既定设计基线在边界内完成代码编写，同步落实错误处理、可测性钩子与性能约束，并将审查中重复出现的人工纠正转化为自动化静态检查或测试门禁。

## 1. 阶段定位与实现原则

实现阶段承接设计与架构基线，并将可执行产物送入第 4 章（验证）与第 5 章（测试与质量保障）构成的正确性层：

**意图与需求 → 设计与架构 →「实现」→ 验证与测试（正确性层）→ 集成与交付 → 持续演进**

在 AI-Native 流程中，代码生成完成**不等于**任务完成，更不代表功能正确或性能达标。实现阶段的核心职责是忠实落地设计契约与预算假设，为后续的独立验证提供可观测、可注入的锚点，而不是自顾自地给出“已通过”的结论。

### 基本原则

- **基线未定不盲目编码**：在缺乏基本接口契约、边界约束与性能预算说明时，不进行大规模实现生成，应先补齐设计基线。
- **严守边界与契约**：严格在分配的模块目录与职责范围内编写代码，优先保障接口前后置条件与不变量成立。
- **最小正确与显式异常**：优先写出逻辑清晰、易于人类审阅的最小必要实现，所有异常、超时与背压拒绝路径必须显式处理，禁止静默吞错。
- **不静默突破设计预算**：不得在不报告的情况下私自突破约定性能或资源上限，无法满足时必须停下并回流至设计层。
- **严禁投机取巧换取绿灯**：不得通过删除既有断言、放松超时阈值或过度替换真实逻辑来制造测试通过的假象。

## 2. 实现产物与可验证性钩子

实现阶段的交付物不仅包含业务功能代码本身，还必须包含支撑下游验证与人工审阅的辅助结构：

| 产物类别 | 具体内容与工程作用 |
|----------|--------------------|
| 模块与契约实现 | 严格按设计职责落地的核心代码，符合既定的输入校验、状态转换与输出语义 |
| 错误处理与背压机制 | 与设计一致的错误码映射、重试边界、队列上限及资源不足时的 Fail-Closed 安全行为 |
| 正确性检查钩子 | 关键不变量断言、状态机只读检查接口以及非确定性依赖（如时钟、I/O）的注入锚点 |
| 性能与资源度量探针 | 围绕热路径预留的计时点、内存/句柄采样计数或稳定的基准测试入口，便于压力与回归测量 |
| 可读诊断与轨迹输出 | 供 Expect 测试、日志审计或人工排查使用的结构化行为摘要与失败上下文快照 |
| 显式设计偏差说明 | 记录实现中发现的设计遗漏、不可测风险或局部结构调整，供设计与 HITL 评审裁决 |

## 3. 编码纪律：将重复纠正沉淀为自动检查

在人类与 Agent 长期协作的代码库中，最常见的流程腐化源于“不断往规则文件或代码注释里堆砌注意事项”。然而，自然语言规则在上下文变长时极易被忽略，代码注释也会随迭代迅速过期，甚至常被用来为临时绕过规则提供借口。**规则文档被跳过时不会主动报错，但自动化检查会。**

因此，实现阶段必须贯彻一条铁律：**同一种人工纠正或低级错误只要在代码审查中出现两次，就必须立刻将其转化为编译器类型约束、Lint 规则、结构依赖检查或自动化测试，而不再仅仅新增一条注释或技能说明。**

具体执行时应遵循以下分工：

1. **能由工具拦截的绝不靠提醒**：诸如跨模块非法引用、未处理的错误返回值、非法的并发访问模式、敏感数据泄露格式等，只要可由静态分析或架构测试自动捕获，就必须沉淀为会阻断 CI 的硬性检查。
2. **注释只留给真正需要人类判断的语义**：只有那些当前技术栈确实无法静态或动态判定的业务权衡与特殊背景，才在代码旁保留简明扼要的说明（说明“为什么必须这样取舍”，而非重复代码字面意思）。
3. **禁止用长篇说明为架构偏差开脱**：如果实现不得不偏离设计边界，应当停下来发起设计修订申请，而不是写一段说明文字试图让违规改动蒙混过关。

## 4. 性能与资源实现约束

在编码落地期间，Agent 必须将设计基线中约定的性能与资源预算纳入日常自检视野，避免将隐患一路带到发布前夕：

| 约束项 | 实现要求 |
|--------|----------|
| 对齐热路径预算 | 实现高频路径时主动对照设计给定的延迟、内存分配与连接句柄上限，避免复杂度退化 |
| 禁止引入隐性开销 | 严禁在热路径中引入无界内存缓冲、隐式同步阻塞锁、重复深拷贝或未受控的日志序列化；确需权衡时须在偏差说明中显式标注 |
| 安全失败优先于指标 | 当遭遇高并发、内存配额耗尽或下游超时时，必须严格依照契约执行 Fail-Closed 退化或背压拒绝，不得为刷高吞吐指标而关闭校验或无限重试 |
| 保障基线可测性 | 保持关键预算路径的接口稳定性或度量钩子，确保测试阶段能够直接挂接微基准或资源剖析工具（Profiling） |
| 偏差及时升级回流 | 若实现中发现现有设计无法在承诺预算内达成目标，应立即中止硬凑，将实测瓶颈反馈回设计层或 HITL 裁决是否放宽预算或调整方案 |

在向正确性层提交代码前，推荐在本地先运行一轮快速的冒烟基准检查或基础资源分配排查，尽早暴露量级上的明显异常；正式的负载、浸泡与门禁核对则交由第 5 章（测试与质量保障）与第 6 章（集成与交付）完成。

## 5. 规范执行流程与质量门禁

1. **核对设计基线与豁免项**：确认上游接口契约、类型边界、性能预算以及标明的“未承诺”范围，缺项即先补齐设计。
2. **在既定边界内推进编码**：按模块逐步完成功能逻辑、状态流转与静态类型约束落地。
3. **显式补全异常与背压路径**：落实所有边界校验、错误传播、超时控制与过载安全失败行为。
4. **植入检查与度量锚点**：接入不变量断言、可插拔测试接口及必要的性能/诊断观测钩子。
5. **收敛重复问题并提交验证**：将反复暴露的编码问题固化为自动检查后，运行本地构建与初步自检，将产物送入第 4–5 章正确性层。

### 质量门禁

- [ ] 全部代码改动严格落在设计划定的模块边界内，满足输入输出契约
- [ ] 异常、超时、背压与安全失败路径均已显式实现，无静默吞错
- [ ] 高风险逻辑具备可观测断言、诊断状态与测试注入钩子
- [ ] 未在未审批的情况下突破已承诺的性能或资源预算（偏差已记录并回流）
- [ ] 关键预算路径具备可供测试层直接测量的稳定接口或度量探针
- [ ] 无未经设计批准的架构级跨界引用或结构漂移
- [ ] 代码结构与命名对后续人类评审（HITL）保持清晰可读
- [ ] 审阅与自检中重复出现超过一次的错误模式已转化为自动化检查或测试，而非新增规劝注释

## 6. 人机职责分工与本章小结

| 角色 | 本章主要工作 | 边界与注意事项 |
|------|--------------|----------------|
| Agent | 依据契约编码、落实错误与预算约束、预留观测钩子、把重复纠正收口成 Lint 或测试 | 记住“实现绿灯不等于正确且不等于达标”，禁止以修改校验规则或删测试的方式绕过失败 |
| 人（HITL） | 审阅结构可读性、裁决设计偏差说明、阻止“为追求速度牺牲安全失败”的短视改动 | 专注于架构健康与重复模式识别，发现连续同类问题时推动固化为自动化检查，而非重回手写编码 |

### 本章小结

- 实现阶段负责将设计与预算忠实转化为可检查的代码产物，它本身**不证明**系统正确性，也不自动保证生产环境性能。
- 靠注释和规劝无法长期约束自动化生成；把重复纠正沉淀为静态检查与测试，才是维持代码库长期健康的工程正道。
