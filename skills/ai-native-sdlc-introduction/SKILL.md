# AI-Native SDLC · 导论

在 AI Agent 已经能够规模化生成代码的条件下，软件交付的稀缺资源不再是编码速度，而是独立于生成者的正确性证据与有界的人工风险裁决。

## 1. 核心命题：从生成速度到正确性证据

**AI-Native SDLC**（AI-Native Software Development Life Cycle）是一套以 AI Agent 为生产与执行主体，由人类提供意图输入并在环内承担最终裁决（HITL），并通过可执行规格、自动化验证与硬性门禁约束交付的软件工程方法。

当代码生成的边际成本大幅下降后，软件工程的核心矛盾也随之转移：写出看似可用的实现并不困难，困难的是在不重新退回人工逐行编写或逐行排查的前提下，**确信交付产物真正满足预期且不破坏现有系统**。

本书要求三项要素在工程流程中同时成立：

1. **人把意图与边界说清楚**：明确当前迭代要解决什么问题、不做什么、如何判定完成，以及哪些风险尚待探索。
2. **Agent 在基线与约束内推进生产**：依照设计与契约生成代码、调试问题并准备验证证据，而不是自由发挥或绕过规则。
3. **独立的系统保证能够否决不合格产物**：任何改动必须通过独立于实现者的检查（端到端运行时路径、自动化测试、静态分析或形式化验证）；检查未通过时，流程强制阻断，不得进入下一阶段。

工程中的信任应建立在**环境结构与可重复执行的检查**之上，而非 Agent 的自我声明。凡是能够固化为目录边界、类型约束、静态规则或可复现验证命令的规范，都不应仅停留在口头提示或规则文档中；人工审阅的重心也应从“逐行核对代码差异”转向“核查关键路径与性质的验证证据”。

### 1.1 与传统研发模式的对照

| 研发模式 | 生产主体 | 人的核心职责 | 系统保证的地位 |
|----------|----------|--------------|----------------|
| 传统 SDLC | 人 | 主导需求分析、架构设计、编码实现与测试编写 | 视团队纪律而定，多为辅助手段 |
| AI 辅助开发 | 人 | 主导核心逻辑与结构编写，借助模型补全或生成片段 | 仍以人工流程和主观评审为主要把关 |
| AI-Native SDLC | Agent | 提供可判定意图、设定门禁，并在 HITL 范围内裁决风险 | 硬性门禁作为晋级必要条件，具备独立否决权 |

### 1.2 瓶颈链条

在 Agent 具备高并发生成能力的前提下，项目能否稳定交付往往取决于以下三个环节：

1. **检查是否独立于实现者**：当 Agent 同时编写实现代码与局部测试时，极易产生同源盲区；项目必须拥有端到端路径、外部规格、模型检查或差异对照等独立校验手段。
2. **门禁是否精确到性质层面**：单纯的“测试全绿”只表示已有用例通过，必须同时记录“本次检查覆盖了哪些性质、哪些条件尚未覆盖”。
3. **人工裁决是否保持有界与清醒**：在海量生成产物面前，人工需要聚焦于意图冲突、例外放行与发布决策，避免因信息过载而盲目信任输出（即认知投降）。

因此，本方法论的主优化目标不是单纯提高代码生成吞吐量，而是建立一条清晰可控的约束链：

**可判定意图 → 可执行规格 → 验证闭环 → 性质级门禁 → 有界人工裁决（HITL）**

如果前端缺乏可判定的意图与清晰的设计边界，后端再严密的自动化检查也只是在高效地验证一个错误的问题。

## 2. 角色与职责：Agent、人与系统保证

要构成符合本书定义的 AI-Native SDLC，必须同时满足以下三项基本要求，缺一不可：

- **R1（生产主体）**：AI Agent 作为默认的代码与工程产物生产主体，在约束内推进实现与修复。
- **R2（意图与裁决）**：人类负责提供并演进意图输入，并作为人在环内（HITL）的关键裁决源，不再以手工编码作为日常生产主体。
- **R3（独立否决）**：系统保证必须具备独立否决权；只要硬性门禁未通过，任何主体都不得放行变更进入下一阶段。

| 角色 | 应承担的职责 | 不应跨越的边界 |
|------|--------------|----------------|
| Agent | 在意图与设计基线内生成实现；执行验证闭环并迭代修复；提交性质级证据与未覆盖清单 | 擅自绕过、削弱或修改拦住自己的门禁；将尚未验证的假设伪装成已锁定性质 |
| 人（意图提供方） | 明确业务目标、验收基准、非目标与硬性约束；随反馈不断修订意图基线 | 要求在第一天就穷尽所有边缘场景，导致前期文档僵化或停滞 |
| 人（HITL 裁决方） | 裁决需求冲突、架构例外、未覆盖风险与正式发布；通过证据与摘要理解系统变化 | 因不信任而退回到逐行手写代码，或因信息过载而放弃核对直接签核 |
| 系统保证 | 提供可重复执行、可留痕的客观校验；在门禁失败时阻断晋级并保留失败上下文 | 替代人类做出商业价值取舍、合规判断或残余风险的责任承担 |

### 2.1 裁决优先级与双受众用法

当流程中出现多方意见或检查结果时，按以下顺序流转：

1. **硬门禁未通过**：流程立即停止，由 Agent 读取失败证据并进入修复闭环（连续多轮无法收敛时上报人类）。
2. **门禁通过且属于 HITL 范围**（如涉及架构偏差、预算豁免、高风险发布或明确标记的未覆盖项）：暂停并等待人工裁决。
3. **门禁通过且在既定基线与策略授权内**：Agent 可直接推进至下一阶段。

本书同时面向两类读者编写：**Agent** 将各章的输入、输出、执行步骤与门禁视为工作契约，未达标即停止并上报；**人类工程负责人与 HITL** 则依据各章框架配置门禁尺度、审阅未覆盖风险并承担最终发布责任。

## 3. 核心术语与规范用语

| 术语 | 工程定义 |
|------|----------|
| AI-Native SDLC | 以 Agent 为生产主体，通过意图约束、独立系统保证与有界人工裁决驱动软件交付的工程体系 |
| Agent | 能够调用工具、读写代码与文档、运行检查并根据反馈自主推进多步任务的执行单元 |
| 生产主体 | 在生命周期中承担主要内容生成、编码实现与修复推进职责的角色，本体系中默认为 Agent |
| 意图输入 | 对目标、边界、非目标、优先级及核心约束的描述，允许初期存在已知未知并随迭代演进 |
| HITL（人在环内） | 人类在关键节点上基于结构化证据进行的监督与裁决；权力高于 Agent，但仍受硬门禁约束 |
| 系统保证 | 不依赖生成者主观陈述的可重复检查体系，包括静态分析、端到端测试、模型检查、仿真与 CI 门禁 |
| 门禁 | 部署在阶段转换或合入边界上的强制性检查规则，未通过时阻断后续推进 |
| 性质级证据 | 同时指明“验证了哪条具体性质”与“哪些边界或条件尚未覆盖”的结果记录，而非笼统的“全部通过” |
| 验证闭环 | Agent 作出改动后主动运行独立检查、解析失败状态并针对性修正，直至满足完成条件或触及升级上限的循环 |

本书在表达约束强度时采用以下规范用语：

- **必须 / 不得**：表示不可违背的硬性约束；除非经过正式的架构或发布例外审批，否则违反即导致门禁失败。
- **应 / 不应**：表示默认遵循的工程实践；若因场景限制需要偏离，需记录原因与补偿措施。
- **可**：表示按需选用的增强手段或实践建议。

## 4. 工程目标与基本原则

### 4.1 五项核心目标

- **G1 缩短交付周期**：由 Agent 承担主要生产与自检迭代，大幅压缩从清晰意图到可运行版本的周期。
- **G2 高风险行为可证伪**：对并发协议、权限隔离、资金状态与资源耗尽等高风险路径建立可复现、可证伪的检查防线。
- **G3 规格、测试与门禁同源**：尽量让验收基准、合约模型与回归检查指向同一份真源，避免文档与实际行为长期脱节。
- **G4 缺陷修复伴随永久回归**：每一次线上故障或审阅纠正都应转化为可执行的回归保护或结构性防错，防止同类问题再次出现。
- **G5 面向人类审阅的高信噪比证据**：用可打开的运行录像、轨迹比对、性能基线和覆盖清单支撑人工裁决，降低人工评审的认知负荷。

### 4.2 九项基本原则

- **P1 意图先行**：允许初期存在待探索的“已知未知”，但必须先明确当前迭代可判定的目标与边界，再进入设计与编码。
- **P2 风险驱动**：不平均分配验证成本，而是依据故障后果与概率决定对哪些模块实施端到端验证、仿真或形式化证明。
- **P3 一切重要结论可检查**：不能只靠规则文档约束行为，重要的规范与经验应尽可能映射为类型检查、Lint 规则或自动化测试。
- **P4 可执行规格优先**：优先使用表格用例、契约断言和属性描述等可被机器直接判定的格式来表达验收标准。
- **P5 闭环反馈可阻断晋级**：验证闭环的权威性来自“确实会失败”，未过门禁的产物不得进入合入或发布队列。
- **P6 表达服务于消歧**：写作格式服务于“让人和 Agent 理解一致”，不将特定的自然语言标准强制绑定为前置门槛。
- **P7 工程经验资产化**：会话记忆是短暂的，真正有效的契约、检查脚本、反例种子与复盘结论必须沉淀进代码仓库。
- **P8 生产主体与约束分离**：执行生成的 Agent 与负责把关的系统门禁相互独立，禁止待合入变更篡改正在校验自己的基准规则。
- **P9 覆盖情况显式化**：任何宣布“通过”的检查都必须诚实列出已查性质与未覆盖范围，杜绝假阳性掩盖风险。

## 5. 全书结构与生命周期映射

本书按照软件演进的自然顺序组织核心章节，其中第 4 章（验证）与第 5 章（测试与质量保障）共同构成核心的**正确性层**，而第 8 章（工具与技能生态）横跨全流程提供底层支撑：

**第 1 章 意图与需求 → 第 2 章 设计与架构 → 第 3 章 实现 → 第 4–5 章 正确性层（验证与测试）→ 第 6 章 集成与交付 → 第 7 章 持续演进**

| 章节 | 名称 | 核心输入 | 关键输出 |
|------|------|----------|----------|
| 第 0 章 | 导论 | — | 方法论定义、人机分工、约束链与术语基准 |
| 第 1 章 | 意图与需求 | 原始业务诉求 | 可判定意图基线、非目标边界、验收标准与已知未知 |
| 第 2 章 | 设计与架构 | 意图基线 | 模块边界、接口契约、非法状态收紧、预算目标与 ADR |
| 第 3 章 | 实现 | 设计基线 | 模块代码、显式错误处理、检查钩子与自动化防错规则 |
| 第 4 章 | 验证 | 契约、属性与实现 | 端到端运行时证据、性质级覆盖记录与按需引入的形式化结论 |
| 第 5 章 | 测试与质量保障 | 验收标准与性能预算 | 多维测试集、行为快照、仿真种子、变异与性能核对报告 |
| 第 6 章 | 集成与交付 | 附带证据包的变更 | 四级门禁记录、可追溯制品、灰度发布与回滚方案 |
| 第 7 章 | 持续演进 | 线上信号与审阅反馈 | 分层根因回流、修复补丁、回归资产与规则清理 |
| 第 8 章 | 工具与技能生态 | 各阶段执行需求 | 结构防错基座、可复用验证命令、最小工具集与判断型 Skill |
| 附录 | 清单 / 术语 / 反模式 / 局限 | — | 全流程核对清单、增补术语、高频反模式及适用边界说明 |

## 6. 适用范围与非目标

**适用场景**：本书适用于业务意图可以分阶段清晰判定，且能够通过自动化工具与 CI 流水线为阶段晋级建立客观门禁的各类软件工程交付团队。方法论本身保持技术中立，不绑定特定的编程语言、形式化证明器或持续集成平台。

**明确的非目标**：本书不替代行业安全认证（如航空、医疗或车规标准的法定合规签字），不强制规定单一的工具链栈，也不承诺能够实现“完全脱离人类监督”或“绝对零缺陷”的软件开发。关于当前版本方法论的已知局限与待探索问题，请进一步查阅附录第 4 节。

所有跨阶段的详细检查条目，以各章质量门禁及 `checklists/master-checklist.md` 为准。
