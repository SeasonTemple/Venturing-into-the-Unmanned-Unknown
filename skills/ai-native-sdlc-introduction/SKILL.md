# AI-Native SDLC · 导论

## 1. 范围

本章规定：

1. AI-Native SDLC 的术语与组成要素
2. 角色职责（规范性）
3. 与传统 SDLC、AI 辅助开发的对照
4. 目标、原则与章节映射
5. 适用范围与非目标

本章不规定具体编程语言、证明器或 CI 产品；实现细节见第 3、5、6、8 章。

---

## 2. 术语

| 术语 | 定义 |
|------|------|
| AI-Native SDLC | 以 Agent 为生产与执行主体，在软件生命周期各阶段推进工作，并以意图输入、HITL 与系统保证共同约束交付的工程方法 |
| Agent | 可调用工具、生成与修改产物、执行检查并推进多步任务的执行单元；允许多个并行或编排 |
| 生产主体 | 承担主要生成、修改、执行与流程推进的角色；本方法中为 Agent |
| 意图输入 | 目标、边界、非目标、优先级与硬约束；主要来源为人及业务渠道；允许不完备并迭代 |
| HITL | Human-in-the-Loop。人对指定事项的环内裁决；权重通常高于自动化建议，但不是唯一否决源 |
| 系统保证 | 可执行规格、静态/类型检查、测试、验证、仿真、CI 等可重复约束 |
| 门禁 | 未通过则不得进入下一阶段的强制检查 |

---

## 3. 规范性要求

采用本方法时，下列要求同时满足：

| ID | 要求 |
|----|------|
| R1 | 生产主体为 Agent。分析、生成、修改、工具调用、执行检查与阶段推进以 Agent 为主路径。 |
| R2 | 人提供意图输入，并作为 HITL 裁决源之一。意图、优先级、非目标与硬约束作为输入；规格冲突、风险例外、发布与合规等可上升 HITL。人不是默认编码生产主体。 |
| R3 | 系统保证可独立否决。硬门禁失败时不得进入下一阶段；不得以口头同意替代已声明的硬门禁。 |

任一要求系统性缺失时，不按本文件定义称为 AI-Native SDLC。

## 4. 角色与职责

### 4.1 职责矩阵

| 角色 | 应做 | 不应做 |
|------|------|--------|
| Agent | 在基线与门禁内生成/修改产物；执行可自动化检查；报告失败与冲突 | 绕过硬门禁；将已知未知表述为已锁定性质 |
| 人（意图源） | 提供与更新意图输入；标示非目标与硬约束 | 要求首轮穷尽全部真实世界性质（见第 1 章） |
| 人（HITL） | 裁决冲突、风险例外、发布/合规；维护可理解性所需定调 | 默认以逐行手写替代 Agent 生产路径 |
| 系统保证 | 对违规给出可重复失败结果；阻断不合格晋级 | 替代 HITL 在价值排序与合规上的判断 |

### 4.2 裁决顺序

1. 硬门禁未通过 → 停止晋级。
2. 硬门禁通过且事项属 HITL 范围 → 等待 HITL 结果。
3. 否则 Agent 可在基线内继续推进。

---

## 5. 与相邻模式对照

| 模式 | 生产主体 | 人的主职责 | 系统保证 |
|------|----------|------------|----------|
| 传统 SDLC | 人 | 分析、实现、测试的执行 | 可选 |
| AI 辅助开发 | 人 | 主体写作；模型补全 | 通常仍按人为主路径组织 |
| AI-Native SDLC | Agent | 意图输入；HITL 裁决（之一） | 门禁为晋级必要条件 |

判据：生产主体是否为 Agent；门禁是否具备独立否决权。

---

## 6. 目标

| ID | 目标 | 度量方向（示例） |
|----|------|------------------|
| G1 | 缩短意图到可运行版本的周期 | 主导航周期时间 |
| G2 | 高风险行为可检查、可证伪、可复现 | 关键路径门禁覆盖；失败复现率 |
| G3 | 多 Agent 与 HITL 共享质量基准 | 规格/测试/门禁同源 |
| G4 | 检查资产可回归 | 缺陷修复附带回归项比例 |
| G5 | 产物可供 HITL 审查 | 变更可说明；关键行为可观察 |

---

## 7. 原则

| ID | 原则 | 说明 |
|----|------|------|
| P1 | 意图先行 | 无意图基线不开展大规模生成；基线可含已知未知 |
| P2 | 风险驱动 | 保证强度按缺陷代价与不确定性分配 |
| P3 | 可检查 | 重要结论可映射到工具或测试结果 |
| P4 | 可执行规格优先 | 表格、属性、契约优先于不可执行长文本 |
| P5 | 反馈闭环 | 类型/测试/验证/仿真失败可阻断或回流 |
| P6 | 表达服务对齐 | 以减少歧义为目的；不强制特定写作标准 |
| P7 | 资产化 | 规格、测试、模型与决策可版本化 |
| P8 | 主体与约束分离 | Agent 生产；意图/HITL 与系统保证约束 |

## 8. 生命周期与章节映射

```
意图 → 设计 → 实现 → 验证/测试 → 集成交付 → 演进
 │      │      │        │            │         │
ch1    ch2    ch4     ch3,ch5       ch6       ch7
                                         工具横切: ch8
```

| 章 | 标题 | 典型输入 | 典型输出 |
|----|------|----------|----------|
| 0 | 导论 | — | 术语与角色约定 |
| 1 | 意图与需求 | 原始描述 | 意图基线、验收、已知未知 |
| 2 | 设计与架构 | 意图基线 | 边界、契约、风险路径、ADR |
| 3 | 验证 | 属性与设计 | 检查结果、反例或通过记录 |
| 4 | 实现 | 设计基线 | 模块代码与可检查点 |
| 5 | 测试与质量 | 验收与契约 | 自动测试；轨迹/种子资产 |
| 6 | 集成与交付 | 已检变更 | 制品、门禁记录、发布/回滚 |
| 7 | 持续演进 | 运行与门禁信号 | 修复、回归、基线修订 |
| 8 | 工具与技能生态 | 环节需求 | 最小工具集与调用约定 |

默认执行方：Agent。门禁与 HITL 为约束接口。

---

## 9. 适用范围

**适用**

- 意图可逐步写成可判定验收，并可为晋级定义门禁的软件交付
- 多 Agent 或高强度自动生成，且需抑制模糊意图放大的场景

**非目标**

- 替代行业认证、安全评估或法定签字
- 指定唯一语言、证明器或仿真产品
- 保证无 HITL 或零缺陷

高保证领域须在本方法之上叠加领域强制标准。

## 10. 用语约定

| 用语 | 含义 |
|------|------|
| 必须 / 不得 | 硬约束（门禁或角色禁区） |
| 应 / 不应 | 默认实践；例外须记录 |
| 可 | 可选 |

检查项以各章门禁列表及 `checklists/master-checklist.md` 为准。
