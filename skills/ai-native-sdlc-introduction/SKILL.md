# AI-Native SDLC · 导论

## 1. 本章定位

本章是全书起点，回答：

- 什么是 AI-Native SDLC
- **谁是生产主体、人与系统各扮演什么角色**
- 它解决什么问题，后续各章如何衔接

---

## 2. 定义

**AI-Native SDLC**（AI-Native Software Development Life Cycle）是指：

> 以 **AI Agent 为生产与执行的主体**，在软件全生命周期中推进澄清、设计、实现、验证、交付与演进；**人**主要提供**原始意图输入**，并作为 **HITL（Human-in-the-Loop）裁决源之一**（通常权重更高）；**系统保证**（可执行规格、自动测试与验证、CI 门禁、仿真等）提供可重复的否决与放行能力。

三点必须同时成立，缺一则容易退回「助手模式」或「无人负责的自动生成」：

1. **主体是 Agent** — 主要分析、生成、修改、调用工具、跑检查、编排多步工作由 Agent 完成（可多 Agent）
2. **人是输入与环内裁决，不是默认生产主体** — 意图、优先级、非目标与硬约束来自人；冲突、风险例外、发布与合规等由 HITL 做权威较高的裁决
3. **系统保证可独立于某次人工心情而否决** — 门禁失败即不可进入下一阶段

它不是「人写主体、AI 补几行」，也不是口号式的「AI 生产 + 人拍板」二分法。

目标不是「人不写、不读代码」，而是在主体切换为 Agent 之后，**意图仍可追溯、关键路径可证伪、产物对 HITL 可理解**——否则裁决无依据，后续 Agent 也难以接续。

---

## 3. 角色分层

| 角色 | 位置 | 不做的事 |
|------|------|----------|
| **Agent（生产主体）** | 设计草案、实现、测试草稿、修复、工具调用、流程推进 | 不自行取消硬门禁；不把未知当成已锁定性质 |
| **人 · 意图源** | 原始目标、价值排序、非目标、组织约束 | 不要求一次穷尽全部性质（见意图章） |
| **人 · HITL 裁决** | 规格冲突、风险例外、发布/伦理/合规、理解型定调 | 不默认用逐行手写代替 Agent 生产 |
| **系统保证** | 类型/契约、测试、验证、仿真种子、CI | 不替代 HITL 在价值与合规上的判断 |

**关键转变：** 从「AI 帮忙」到 AI-Native，本质是 **生产主体从人切换为 Agent**；人退到**意图输入 + 权威较高的环内裁决**；质量由 **HITL 与系统保证共同约束**。人的稀缺资源是注意力与判断，不是键入量。

---

## 4. 与相关概念的区别

| 模式 | 生产主体 | 人的主角色 | 典型局限 |
|------|----------|------------|----------|
| 传统 SDLC | 人 | 分析、编码、测试的执行者 | 速度受人力瓶颈限制 |
| AI 辅助开发 | 仍是人 | 主体写作；AI 补全片段 | 主体未切换；缺少系统化验证与流程 |
| **AI-Native SDLC** | **Agent** | 意图输入 + HITL 裁决源之一 | 依赖意图可判定性、门禁与表达纪律；需承认意图渐进完备 |

---

## 5. 核心目标

1. **速度** — 由 Agent 主体缩短意图到可运行系统的周期
2. **可靠性** — 高风险路径可检查、可证伪、关键失败可复现
3. **可协作** — 多 Agent 与 HITL 共享表达与质量基准
4. **可演进** — 属性、测试、模型与决策可沉淀、可回归
5. **可理解** — 仓与行为对 HITL 可读，裁决与后续 Agent 工作才成立

---

## 6. 基本原则

- **意图先行** — 先有可迭代的意图输入，再大规模生成；不要求一次锁全性质
- **风险驱动** — 高风险路径施加更强保证
- **可检查性** — 重要结论可被工具或测试验证；系统保证与 HITL 并列
- **可执行规格优先** — 表格、属性、契约更易被 Agent 与门禁消费
- **快速可读反馈** — 类型/结构、Expect、仿真种子等缩短闭环
- **表达以对齐为目的** — 降歧义；具体写作标准可选，非依赖
- **资产化** — 属性、模型、测试、决策可维护
- **主体与约束分离** — Agent 生产与执行；人提供意图并参与 HITL；门禁提供可重复约束

## 7. 全书结构

| 章 | 标题 | 作用 |
|----|------|------|
| 0 | 导论 | 定义、角色、原则、总览 |
| 1 | 意图与需求 | 意图输入如何澄清、可判定、渐进完备 |
| 2 | 设计与架构 | 组织方式；不变量与可仿真边界 |
| 3 | 验证 | 是否正确、是否可保证 |
| 4 | 实现 | Agent 如何在约束下产出实现 |
| 5 | 测试与质量保障 | 行为层保证 |
| 6 | 集成与交付 | 系统门禁与发布 |
| 7 | 持续演进 | 反馈、HITL 纪律与回归 |
| 8 | 工具与技能生态 | Skill / MCP / CLI |

各章默认读者是 **作为生产主体的 Agent** 与配置流程的人；门禁与 HITL 是约束，不是把人重新写成唯一执行者。

---

## 8. 适用边界

- 适用于可将意图逐步可判定、并愿意建立门禁的软件交付
- 高保证领域须叠加行业形式化与认证要求；本书是方法骨架，不是合规替代
- 原则跨语言；工具按生态成熟度与风险选用
- 不承诺「无 HITL、全自动正确」；承诺 **Agent 主体 + 意图/HITL + 系统保证** 的可检查流程
