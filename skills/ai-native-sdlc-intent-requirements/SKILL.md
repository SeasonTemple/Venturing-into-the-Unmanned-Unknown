# AI-Native SDLC · 意图与需求

## 1. 本章定位

### 1.1 所属环节

意图与需求是 AI-Native SDLC 的起点，位于所有设计、实现与验证之前。

**「意图澄清」→ 设计 → 实现 → 验证 → 交付 → 演进**

意图基线会随学习**回流修订**（见持续演进章），不是写一次就永恒完备。

### 1.2 地位与意义

在 AI-Native 模式下，生成成本极低，错误意图的成本被放大。
若意图模糊，Agent 会高速产出错误实现，并沿错误方向自动化扩散；多 Agent 还会因歧义产生理解冲突。

本章解决：

- 要做什么（目标）
- 不做什么（边界）
- 怎样算完成（验收，**优先可判定、可执行**）
- 如何减少误解（**目的是对齐理解，不是套用某份写作标准**）
- 在**无法一次说全**所有性质时，如何仍可开工并可控地补全

### 1.3 核心价值

- 降低返工与 Agent 跑偏
- 为验证提供可追溯属性来源（允许先少后多）
- 为多 Agent 提供当前迭代的统一理解
- 使人的裁决集中在目标与风险，而不是幻想「需求一次完备」

## 2. 理论框架

### 2.1 意图层的三个产物

| 产物 | 作用 |
|------|------|
| 目标陈述 | 说明系统要达成的结果 |
| 约束与边界 | 说明范围、非目标、限制条件 |
| 验收标准 | 说明如何判定完成（可观察、可判定；能写成测试/属性更佳） |

三者必须可被观察、可被判定，避免空泛描述。**不要求**在第一轮就覆盖全部真实世界约束。

### 2.2 实践约束：性质与禁止行为无法一次锁全

「锁定必须成立的性质与禁止行为」是**方向**，不是「开工会前必须穷尽宇宙」。

实践中常见：

- 业务方自己也说不清边界情况
- 有些不变量要到设计或实现对抗后才暴露
- 有些禁止行为要等故障、审计或 Agent 冲突才被命名
- 过早追求「性质全集」会拖延交付，或写出无法维护的伪完备文档

因此本书采取：

**风险优先的最小可判定意图 → 可执行反馈发现缺口 → 显式修订意图基线。**

#### 2.2.1 第一轮至少要锁住什么

| 优先级 | 内容 | 说明 |
|--------|------|------|
| P0 | 主成功路径的可观察目标 | 没有它无法判断「做完了没有」 |
| P0 | 明确非目标 / 范围外 | 防止 Agent 顺手做大 |
| P0 | 已知的高代价禁止行为（若已知道） | 如：不允许双写者、不允许静默丢单 |
| P1 | 已知边界与失败时的可观察表现 | 超时、拒绝、只读等 |
| P2 | 尚不清楚的区域 | **标成「已知未知」**，指定用哪类手段去发现（见下表） |

「已知未知」写进意图是合格做法，不是缺陷。

#### 2.2.2 用全书手段补全性质（闭环）

| 发现缺口的信号 | 主要回到哪一层 | 典型手段（见对应章） |
|-----------------|-----------------|------------------------|
| 人/Agent 对同一句两种理解 | 意图 | 正反例、表格验收、改写句子 |
| 实现分叉、差异测试失败 | 意图或设计 | 差异测试、补规格案例 |
| 属性/场景测试失败 | 意图或实现 | 属性测试、表驱动；修订性质陈述 |
| 并发/协议反例 | 设计或意图 | 模型检查；可能上修不变量 |
| 偶发不可复现故障 | 测试/设计 | DST 种子、库级仿真；抽象出新禁止行为 |
| 线上事故或审计 | 演进 → 意图 | 止损、复盘、把新性质写入基线与回归 |

形式化验证、契约、Expect、DST 等**不是**要求意图阶段一次写全，而是**把「事后发现的必须成立」固化成可检查资产**的手段。

#### 2.2.3 与「可执行规格优先」的关系

- 意图阶段：能写成表格或一句话性质的，先写成；写不出的标未知
- 不要用长篇自然语言假装已经覆盖
- 每发现一条真性质，优先落成**可执行**回归（测试、属性、模型、仿真种子），再改意图文档——避免文档与行为再次分叉

### 2.3 表达：先目的，再手段

**核心目的（必须先满足）：**

1. **同一句话尽量只有一种合理理解**（人与 Agent 对齐）
2. **当前基线内的完成与否可判定**
3. **边界与已知未知都写清楚**（含非目标）

**推荐的写法习惯（不绑定某一标准）：**

- 短句；主动语态；一句一个主要意思
- 关键术语尽量一词一义；主体与动作写清楚
- **正例 + 反例**成对出现，压缩「第二种理解」
- 验收优先表格或「对所有…应…」式性质，而不是形容词堆砌

若团队已有术语表、模板或评审清单，优先用现有资产达成上述目的即可。

**可选参考：受控技术英语（STE）实用子集**

[ASD-STE100](https://www.asd-ste100.org/) 是航空等领域使用的受控技术英语规范。**本书不要求符合完整 ASD-STE100**，也不把任何 STE 工具当作流程依赖。仅在英语文档且歧义已造成成本时，**建议**借鉴其实用子集；中文等语言对齐的是同一目的与习惯，而非英语词表。检查类 Skill 可选安装，可随时不用。

### 2.4 从意图到验证与测试的映射

| 意图要素 | 后续用途 |
|----------|----------|
| 已锁定的必须规则 | Safety 属性、不变量、类型/模型约束 |
| 已锁定的最终结果 | Liveness 属性 |
| 边界与异常 | 测试场景、失败路径、Expect 轨迹 |
| 接口约定 | 契约与模块验证 |
| 并发/恢复线索 | 模型检查、库级/全系统确定性仿真候选 |
| 已知未知 | 显式探索任务：差异测试、fuzz、仿真、评审 |

## 4. 规范执行流程

1. **收集原始意图** — 记录原始描述，不急于设计
2. **澄清与消歧** — 主体、成功/失败行为、非目标；追问第二种理解
3. **划分已锁定 vs 已知未知** — P0/P1 写可判定验收；未知写明探索方向
4. **可执行化** — 能表格化/性质化的先落地；不硬编假完备
5. **识别风险线索** — 并发、状态机、权限、恢复（供设计/验证/DST）
6. **确认当前迭代基线** — 冻结的是「这一轮」；允许按演进流程修订
7. **（后续）缺口回流** — 测试/验证/线上信号触发时，回本层补性质并加回归

### 质量门禁

- [ ] 目标可观察
- [ ] 边界清晰（含非目标）
- [ ] **当前基线内**验收可判定（不要求一次覆盖全部真实约束）
- [ ] 关键已锁定验收有表格或属性线索
- [ ] 重要「已知未知」已标明，而非假装已定义
- [ ] 关键歧义已消除
- [ ] 已标出高风险线索
- [ ] （若为修订）变更有记录，且配套回归已更新或已建项

## 5. 简洁实例

**原始：** “做一个文档锁定功能，别让人同时改。”

**第一轮可锁定：**

- 目标：同一文档在同一时刻最多一个编辑者可以写入。
- 非目标：不做实时全文协同编辑。
- 验收：第二人申请写锁 → 明确拒绝或等待；释放/超时后他人可获得；只读始终可开。
- 表格：`(持锁中, 第二人申请) → alreadyLocked` 等。

**第一轮已知未知（示例）：**

- 多机房时钟偏差下超时是否仍安全？→ 设计/模型检查或仿真再定
- 持锁进程崩溃是否自动释放？→ 实现与故障场景测试后补禁止「永久锁死」
- 管理员是否可强拆锁？→ 产品未定，标未知，默认本迭代不做

后续用属性测试、差异测试、DST 或事故复盘把未知变成可执行性质，再改基线——而不是在第一天写一篇「完备锁协议论文」。

---

## 6. Agent 执行要点

1. 先澄清目的与**当前可判定**验收，后生成方案或代码
2. 禁止为显得专业而编造未确认的全量不变量
3. 对未知显式标注，并建议发现手段（测试/验证/评审）
4. 冲突与失败优先补例子与回归，再扩自然语言
5. 不因「未使用某写作标准」或「性质列表不长」判定不合格；看可判定性与风险是否裸奔

---

## 7. 本章要点

- 意图层给出**当前迭代**的方向与可判定完成条件，而不是一次穷尽所有性质
- **目的**是对齐理解与可判定完成；表达标准可选，非依赖
- 「已知未知」合法；用验证、测试、仿真、演进把缺口变成可执行资产
- 风险优先锁定高代价禁止行为；其余用反馈闭环渐进补全
