# AI-Native SDLC · 意图与需求

## 1. 本章定位

### 1.1 所属环节

意图与需求是 AI-Native SDLC 的起点，位于所有设计、实现与验证之前。

**「意图澄清」→ 设计 → 实现 → 验证 → 交付 → 演进**

### 1.2 地位与意义

在 AI-Native 模式下，生成成本极低，错误意图的成本被放大。
若意图模糊，Agent 会高速产出错误实现，并沿错误方向自动化扩散；多 Agent 还会因歧义产生理解冲突。

本章解决：

- 要做什么（目标）
- 不做什么（边界）
- 怎样算完成（验收，**优先可判定、可执行**）
- 如何减少误解（**目的是对齐理解，不是套用某份写作标准**）

### 1.3 核心价值

- 降低返工与 Agent 跑偏
- 为验证提供可追溯属性来源
- 为多 Agent 提供统一任务理解
- 使人的裁决集中在目标，而不是细节修补

## 2. 理论框架

### 2.1 意图层的三个产物

| 产物 | 作用 |
|------|------|
| 目标陈述 | 说明系统要达成的结果 |
| 约束与边界 | 说明范围、非目标、限制条件 |
| 验收标准 | 说明如何判定完成（可观察、可判定；能写成测试/属性更佳） |

三者必须可被观察、可被判定，避免空泛描述。

### 2.2 表达：先目的，再手段

**核心目的（必须先满足）：**

1. **同一句话尽量只有一种合理理解**（人与 Agent 对齐）
2. **完成与否可判定**（能观察、能写成检查或测试）
3. **边界清楚**（含非目标，避免范围漂移）

规格无法穷尽实现细节；意图层应锁定**必须成立的性质与禁止行为**，细节留给设计/实现，并用可执行验收约束。

**推荐的写法习惯（不绑定某一标准）：**

- 短句；主动语态；一句一个主要意思
- 关键术语尽量一词一义；主体与动作写清楚
- **正例 + 反例**成对出现，压缩「第二种理解」
- 验收优先表格或「对所有…应…」式性质，而不是形容词堆砌

这些习惯来自技术写作与需求工程的常识实践。若团队已有术语表、模板或评审清单，优先用现有资产达成上述目的即可。

**可选参考：受控技术英语（STE）实用子集**

[ASD-STE100](https://www.asd-ste100.org/) 是航空等领域使用的受控技术英语规范，用词表与句式规则强制降歧义。**本书不要求符合完整 ASD-STE100**，也不把任何 STE 工具当作流程依赖。

仅在下列情况**建议**借鉴其**实用子集**（业界常称「用到约 80% 有用规则」的做法，而非认证级全文合规）：

- 文档主要用英语撰写，且歧义已造成返工
- 希望有一份现成的「禁用模糊词 / 优先句式」清单可对照
- 可选安装检查类 Skill 做辅助，**可随时不用**

中文或其他语言：对齐的是**同一目的与习惯**（短句、一词一义、正反例、可判定验收），而不是生搬英语词表。

### 2.3 从意图到验证与测试的映射

| 意图要素 | 后续用途 |
|----------|----------|
| 必须永远成立的规则 | Safety 属性、不变量、类型/模型约束 |
| 最终必须发生的结果 | Liveness 属性 |
| 边界与异常 | 测试场景、失败路径、Expect 轨迹 |
| 接口约定 | 契约与模块验证 |
| 并发/恢复线索 | 模型检查、库级/全系统确定性仿真候选 |

## 4. 规范执行流程

1. **收集原始意图** — 记录原始描述，不急于设计
2. **澄清与消歧** — 明确主体、成功行为、失败行为、非目标、限制；追问「是否还有第二种理解」
3. **结构化表达** — 输出目标、约束、验收标准（满足 §2.2 的三个目的）
4. **可执行化** — 能表格化的验收写成输入→输出/错误；能性质化的写成「对所有…应…」
5. **识别风险线索** — 并发、状态机、权限、边界、失败恢复（供设计/验证/DST）
6. **确认与冻结** — 形成当前迭代意图基线，变更需显式记录

### 质量门禁

- [ ] 目标可观察
- [ ] 边界清晰（含非目标）
- [ ] 验收标准可判定
- [ ] 关键验收有表格或属性线索（可执行方向）
- [ ] 关键歧义已消除（人/Agent 对同一句不应有第二种常理解释）
- [ ] 表达简短、主体动作清楚（不强制任何写作标准合规）
- [ ] 已标出高风险线索

## 5. 简洁实例

**原始：** “做一个文档锁定功能，别让人同时改。”

**澄清后：**

- 目标：同一文档在同一时刻最多一个编辑者可以写入。
- 约束：允许多个用户同时打开只读视图；网络断开时，持锁方在超时后释放锁。
- 验收：
  1. 第二位用户请求写锁时收到明确拒绝或等待状态。
  2. 锁持有者释放或超时后，其他用户可以获得写锁。
  3. 只读用户始终可以打开文档。
- 表格线索：`(持锁中, 第二人申请) → alreadyLocked`；`(超时后, 申请) → 成功`。
- 风险线索：并发获取锁、超时释放、重复进入 → 设计/验证/仿真候选。

（上例达成的是「可判定、少歧义」，并不依赖 STE 词表。）

---

## 6. Agent 执行要点

1. 先澄清目的与验收，后生成方案或代码
2. 把模糊词逼成可判定语句；优先正反例与表格
3. 强制区分：目标 / 非目标 / 验收
4. 为验证与测试预留属性与场景线索
5. 不因「未使用某写作标准」而判定意图不合格；以是否可判定、是否仍歧义为准

---

## 7. 本章要点

- 意图层决定后续方向；Agent 时代歧义成本更高
- **目的**是对齐理解与可判定完成，不是绑定 ASD-STE100 或任何单一规范
- 受控表达习惯是**建议**；STE 实用子集是英语场景下的**可选参考**
- 验收标准必须可判定，并尽量可映射到测试/属性
