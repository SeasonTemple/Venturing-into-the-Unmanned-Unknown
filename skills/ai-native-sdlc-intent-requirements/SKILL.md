# AI-Native SDLC · 意图与需求

在编码启动之前，先将当前迭代能够判定的目标、边界与验收路径固定下来，同时把尚不明确的边缘条件如实登记为“已知未知”。

## 1. 阶段定位：为什么意图澄清先于生成

意图与需求处于整个研发链条的起点，位于所有架构设计、编码实现与系统验证之前：

**「意图与需求」** → 设计与架构 → 实现 → 验证与测试 → 集成与交付 → 持续演进

当生产主体转向 AI Agent 后，代码生成的速度成倍提升，但**错误意图带来的返工成本也被同等放大**。如果上游描述含糊不清，Agent 会以极快的速度沿着错误假设生成整套实现与配套测试，多 Agent 协同时更会因各自脑补而产生严重的结构冲突。

因此，本章需要解决四个实际问题：

1. **界定目标与边界**：清晰陈述本轮要达成什么结果，以及明确哪些关联需求**不在本轮范围之内**，防止 Agent 在实现中擅自扩张功能面。
2. **确立可判定的完成标准**：优先从真实用户的端到端操作路径出发定义“怎样算完成”，避免仅靠孤立的单元测试通过来掩盖断裂的交互或业务链路。
3. **建立低歧义对齐**：让人类提出的需求与 Agent 的理解指向同一套事实，依靠清晰语义与正反例对齐，而不是机械套用某种写作规范。
4. **应对天然的不完备性**：承认真实项目无法在第一天写全所有性质与边缘情况，建立“风险优先开工、闭环渐进补全”的迭代机制。

---

## 2. 意图基线的核心构成

每一轮迭代启动前，意图基线应当包含以下四项结构化要素（参考 `templates/intent-template.md`）：

| 构成要素 | 核心作用 | 工程判定要求 |
|----------|----------|--------------|
| 目标陈述 | 阐明系统在本轮迭代后应当达成的业务或技术结果 | 必须具备可观察的外部效果，避免使用“提升体验”“更加稳定”等空泛形容词 |
| 范围与非目标 | 划定实现边界、前置假设与显式排除项 | 明确写出“本轮不做哪些能力”，防止 Agent 过度设计或改动非目标模块 |
| 可判定验收标准 | 规定如何客观判定目标是否达成 | 优先采用可执行的端到端用户路径、输入输出状态表或明确的属性断言 |
| 已知未知与风险线索 | 登记当前尚未敲定的策略以及潜在的并发、权限或资源风险 | 允许保留悬而未决的边界，并指明应在后续哪个阶段通过何种手段查明 |

需要强调的是，**意图基线并非写完即永久冻结的静态文档**，它会随着下游设计对抗、验证反例以及线上运行反馈持续回流修订（详见第 7 章持续演进）。

## 3. 渐进锁定：处理不完备性质的闭环机制

要求在开工前“穷尽所有不变式与禁止行为”在现实工程中往往不可行：业务方最初也未必清楚所有极端边界，许多系统不变式直到接口碰撞、并发压测或故障暴露后才能被准确命名。一味追求起跑前的绝对完备，只会导致流程僵化或产出大量脱离实际的文档。

因此，本方法论采用**渐进锁定策略**：

**风险优先的最小可判定基线 → 下游可执行反馈暴露缺口 → 显式补全性质并修订意图基线**

### 3.1 第一轮迭代至少要锁住什么

| 优先级 | 锁定内容 | 工程目的 |
|--------|----------|----------|
| P0（必须锁定） | 主成功路径的可观察目标与端到端完成定义 | 没有明确的用户路径终态，就无法客观判定任务是否完成 |
| P0（必须锁定） | 明确的非目标与改动禁区 | 约束 Agent 行动边界，避免引发无谓的连锁重构 |
| P0（必须锁定） | 已知的高代价禁止行为（若业务层面已明确） | 例如：严禁同一文档出现双写覆盖、严禁支付指令静默丢失 |
| P1（应当明确） | 已知关键边界与异常下的可观察表现 | 明确超时、权限拒绝、资源只读或降级时的对外行为 |
| P2（显式留白） | 尚不清晰的边缘规则与复杂场景 | 明确标记为“**已知未知**”，并指明后续由设计、仿真或人工裁决补齐 |

把尚无定论的问题坦诚地写为“已知未知”，是高质量工程意图的体现，远胜于在文档中编造看似严谨的假定。

### 3.2 通过全书闭环逐步补全性质

当下游阶段暴露出意图盲区时，按如下路径回流并转化为可执行资产：

| 暴露缺口的信号 | 主要回流层级 | 补全与固化手段 |
|----------------|--------------|----------------|
| 人与 Agent 对同一句话产生两种合理解读 | 意图层 | 补充正例与反例对照、改写歧义条款或转为状态表格 |
| 多实现分支行为不一致或差异测试失败 | 意图层或设计层 | 补充规格边界案例，修订接口契约前置/后置条件 |
| 属性测试（PBT）或场景测试失败 | 意图层或实现层 | 将失败边界抽象为显式规则，补充表驱动回归用例 |
| 并发交错或协议状态机出现反例 | 设计层或意图层 | 借助模型检查修正设计假设，必要时上修业务不变量 |
| 偶发且难以复现的时序或恢复故障 | 测试层或设计层 | 留存确定性仿真（DST）种子，沉淀出新的系统禁止行为 |
| 线上事故或外部安全审计发现漏洞 | 演进层 → 意图层 | 止损复盘后，将新性质写入意图基线与永久回归门禁 |

每当团队在后续阶段发现一条必须成立的新性质时，**应优先将其固化为可执行的回归资产**（如端到端断言、属性测试、模型不变式或仿真种子），再同步更新意图基线，防止文档描述与系统真实行为再次分叉。

## 4. 低歧义表达原则与下游映射

### 4.1 表达原则：对齐理解优于形式教条

撰写意图与需求文档的核心目的只有三点：

1. **消除二义性**：同一条要求在人与不同 Agent 之间尽量只有一种合理理解。
2. **保证可判定性**：基线范围内的完成与否能够被客观检查，而不依赖主观“感觉不错”。
3. **诚实划界**：目标、非目标与已知未知并列清晰呈现。

为达成上述目的，推荐采用以下写作习惯：尽量使用短句与主动语态，每句话只表达一个核心动作；关键领域术语保持一词一义，明确动作发出者与接收者；**用成对的“正例 + 反例”来压缩隐含歧义**；对状态转换和输入输出条件优先使用二维表格或“在满足条件 X 时，系统应保证 Y”的陈述句，而不是堆砌修饰语。

若涉及英文技术文档且歧义已造成较高返工成本，可参考航空等领域使用的受控技术英语规范 [ASD-STE100](https://www.asd-ste100.org/) 的精简原则；中文或其他语言团队只需践行上述消歧原则即可，**本书不把任何受控语言规范或写作检查器设为前置强制依赖**。

### 4.2 从意图要素到验证与测试资产的映射

| 意图基线要素 | 在设计与正确性层中的去向 |
|--------------|--------------------------|
| 已锁定的必须成立规则 | 转化为架构不变量、类型约束及验证章的 Safety 性质 |
| 已锁定的最终状态要求 | 转化为异步流程契约与 Liveness 性质（附带假设条件） |
| 边界条件与异常预期 | 转化为错误码表、失败路径用例与 Expect 行为轨迹 |
| 跨模块或对外协作约定 | 沉淀为设计层的接口契约与模块验证边界 |
| 并发、时序与故障恢复线索 | 标记为设计层模型检查或确定性仿真（DST）重点候选 |
| 显式登记的“已知未知” | 拆解为架构调研、差异测试、模糊测试（Fuzz）或人工裁决任务 |

### 4.3 实用工具准备

在工具选型上，建议优先准备好结构化的意图模板（goal / non-goal / acceptance / known-unknowns）、表格化的验收草稿以及需求 ID 与属性之间的简易追踪记录；仅当跨国英文项目确有需要时，再按需引入英语受控写作辅助检查工具（如可选安装的 `asd-ste100-skill`），切勿本末倒置让文本格式检查阻断业务澄清。

## 5. 规范执行流程与质量门禁

1. **收集原始诉求**：完整记录需求背景与用户痛点，暂不急于跃入技术选型与代码细节。
2. **边界澄清与消歧**：明确交互主体、主路径、异常表现与非目标范围，主动追问容易被误解的第二种解释。
3. **切分已锁定项与已知未知**：锁定本轮 P0/P1 级别的可判定目标，将暂不明朗的边缘策略登记为 P2 已知未知。
4. **验收条件可执行化**：将关键完成标准改写为端到端用户路径描述、状态迁移表或属性陈述，杜绝伪完备长文。
5. **标注高风险线索**：提前标出并发竞争、状态机、权限校验、资金或性能敏感路径，提示设计与验证层重点关注。
6. **冻结本轮意图基线**：明确当前迭代的开工边界；明确后续发现新约束时走受控修订流程。
7. **接收下游缺口回流**：当设计、验证或测试暴露规则盲区时，及时回补性质并附带回归项。

### 质量门禁

- [ ] 核心目标具备可观察结果，且完成定义优先由端到端用户路径刻画
- [ ] 范围边界与明确“非目标”已写清，可约束 Agent 不擅自扩权
- [ ] 当前迭代内的验收标准可客观判定（无强求第一轮覆盖宇宙的虚假完备）
- [ ] 关键规则已配有状态表格、正反例或属性描述
- [ ] 尚未确定的关键边界已明确登记为“已知未知”，并写明后续查证方式
- [ ] 涉及并发、权限、恢复或关键性能的高风险线索已标出
- [ ] 若本基线属于修订变更，修改原因与配套回归更新已关联记录

## 6. 工程实例：文档独占写锁的意图基线

**原始业务诉求**：“给协作系统加一个文档锁定功能，防止两个人同时编辑把内容互相覆盖了。”

若直接将这句话交给 Agent，极易引发关于超时机制、管理员权限、断网恢复或协同编辑的无数次盲目生成。经过本阶段澄清，第一轮迭代的最小可判定基线如下：

- **可观察目标**：任意时刻，同一份文档最多只允许一个活跃编辑会话持有写入权并提交修改。
- **明确非目标**：本轮不实现实时多人协同光标同步，也不实现跨编辑器的内容自动合并冲突。
- **可判定验收（端到端路径与状态表）**：
  - 用户 A 打开文档获取写锁并保存成功；此时用户 B 在界面申请编辑同一文档，系统必须明确拒绝写入请求或展示只读提示，不得静默覆盖 A 的保存结果。
  - 用户 A 主动关闭释放锁或锁租约到期后，用户 B 再次申请应成功获得写锁并完成保存；只读预览视图在锁存在期间始终正常打开。
  - 核心状态迁移矩阵：`(空闲, 申请写锁) -> 授权并持锁`；`(已被 A 持锁, B 申请写锁) -> 拒绝(alreadyLocked)`；`(已被 A 持锁, 只读查看) -> 正常返回只读快照`。
- **第一轮已知未知（显式留白与追踪去向）**：
  - 多机房时钟存在偏移时，基于租约的超时释放是否会导致短暂双写？→ 移交设计层与模型检查阶段界定租约安全边界。
  - 持锁客户端进程异常崩溃未发送释放请求时，何时允许其他用户接管？→ 待超时与故障恢复场景测试后，补入防永久锁死约束。
  - 管理员是否需要强行打破他人写锁的后台入口？→ 产品尚未拍板，标记为未知，默认本轮不开发该入口。

通过这一份精炼的基线，开发团队与 Agent 既能立即开工实现并跑通端到端路径，又把真正危险的时钟与崩溃问题稳妥地挂接到了下游设计与验证章节，而不必在第一天就去撰写一篇“完备分布式锁论文”。

## 7. 人机职责分工与本章小结

| 角色 | 本章主要工作 | 边界与注意事项 |
|------|--------------|----------------|
| Agent | 主动追问模糊诉求、拆解边界与非目标、起草表格验收并标出已知未知 | 严禁为了显得专业而自行编造未经业务确认的全局不变式；不将文本格式规范当作拒绝澄清的借口 |
| 人（意图/HITL） | 确认 P0 业务目标、敲定范围取舍、拍板高代价禁止行为 | 允许阶段性留白，重点审核“哪些风险本轮先放行”以及“已知未知是否都有验证去向” |

### 本章小结

- 意图阶段提供的是**当前迭代**的明确方向与可判定验收基线，而非试图在开工前穷尽全部现实约束。
- 表达纪律的唯一检验标准是“人与 Agent 理解对齐、完成条件可判定”，格式工具仅为辅助手段。
- 坦诚标注“已知未知”，并依托下游验证、测试与演进闭环将其逐步转化为可执行资产，是应对复杂未知区域的稳健之道。
