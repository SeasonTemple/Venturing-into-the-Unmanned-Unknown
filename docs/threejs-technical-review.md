## 逐项取舍

| 建议 | 当前决定 | 如何落实 |
|---|---|---|
| 灯光、模型、相机、后处理、入口模块分离 | 采纳 | 另将任务规则与渲染分离，避免画面逻辑决定验收结果 |
| 一处管理 renderer、resize、循环与 dispose | 采纳并补全 | resize 使用容器尺寸；后台暂停；取消 RAF；释放监听与 GPU 资源；重复进入退出可验证 |
| 加载状态与错误退路 | 采纳 | 进入准备期间保留正常首页；失败能阅读和重试，减少动态效果不阻断任务 |
| 控制相机范围，避免穿模 | 采纳 | 短进入路径、明确落点；转场与用户控制不同时写相机 |
| GLB、纹理优化、性能量测 | 采纳 | 精模阶段先检查资产，再选压缩；记录多 pass 绘制、帧间隔、传输与 GPU 资源 |
| 桌面与移动分别取景，限制 DPR | 采纳 | 桌面 ≤2、移动 ≤1.5，窄屏布局和阅读面独立检查 |
| 使用 Next.js + R3F 替换现有框架 | 当前不采纳 | 延续既有 Astro 与原生 Three.js，先完成灰盒闭环，再依据实际维护问题评估 |
| 强制 HDRI city/sunset、Bloom、暗角、自动旋转 | 改为按任务选择 | 灰盒先用一处主投影光和补光；不加入无意义循环、强发光或遮蔽信息的后处理 |
| 每个大模型都运行 gltfjsx 并视为启用 Draco | 调整 | gltfjsx 是 React 组件工具；原生资产不需要转 JSX。压缩类型以实际导出扩展及解码依赖为准，不能仅凭 `-T/-t` 推断 |
| 开发调试面板 | 按需 | 灰盒先暴露最少量可读状态；确需参数 GUI 时再增加依赖，生产界面不带调试工具 |
| 安装 DSH 插件与 VS Code 扩展 | 暂不安装 | 当前运行环境及需求未证明需要；文中列出的第三方插件可用性与能力未独立验证 |

## 示例代码需要补充的地方

- 示例 `dispose()` 没有取消递归 RAF。释放 renderer 后仍调度渲染会造成异常或重复循环。
- 释放 material 不会自动释放它引用的全部纹理；环境贴图、PMREM 目标、阴影、后处理 render target 和加载器资源须按所有权清理。
- 控制器、ResizeObserver、文档事件与异步加载结果需要撤销或作废。
- 共享纹理与几何要避免被一个模块提前释放；不能把 R3F 的自动处理理解为所有资源均有通用引用计数。
- 后处理的输出色彩与 tone mapping 要有明确管线，不重复套用色调映射。单一 renderer 的正常渲染和 composer 不是同时各画一遍。
- 原生手写并不天然更快，R3F 也不天然更可靠；应以实际结构、负载与检查结果判断。

## 第一版执行边界

先做一个独立、可打开的 Three.js 灰盒原型：正常预览入口 → 进入 → 相同中继任务的两种职责 → 一章真实内容 → 使用检查方法 → 局部恢复 → 相同环境变化 → 返回。

首版不引入新框架、外部 LLM、付费模型或未经核验插件。保留可复放的任务规则、键盘入口、静态降级和明确的证据状态。精模、GLB 压缩、HDRI 与复杂后处理放到路径得到验证之后。

## 2026-10-27 补充：NPR、程序几何、解析动效与并行契约

用户提供一份以港口、水体、雨景为例的技术说明，随后明确：**只吸取其中有价值的技术事项。** 该说明不构成题材、色调、角色造型或框架变更要求；不因出现多代理架构说明而自动启动代理开发。Jusant、INSIDE、Death Stranding 是用户认可的参考组，美术方向仍需实际画面分析。

### 采纳为工程方法

- **集中材质管理**：共享色板、受光／阴影规则、粗糙度与可选描边参数。先在少量代表物件上校准，避免每个模块形成不同风格。是否 NPR、水彩或 PBR 由视觉方向决定。
- **空间契约**：统一单位、坐标轴、原点、局部包围盒、移动和操作区域。包围盒用于集成检查，不能替代空间构图与美术设计。
- **共享时间和环境状态**：由唯一渲染循环分发受控模拟时间、天气和必要的环境采样函数；模块注册更新并获得注销接口。后台、离屏、暂停和减少动态效果有一致规则。FSM 的状态与开始时间单独管理，不能只靠一个 uTime 表达所有交互。
- **资源所有权和模块生命周期**：模块明确创建、共享和释放的资源，暴露 dispose、交互锚点及可选 update；子模块不自行增加 renderer 或永久 RAF。共享材质、纹理不被局部模块提前销毁。
- **按重复方式优化**：同几何同材质的重复物件按区域使用 InstancedMesh；不同静态几何按材质合并。实例化按材质、groups、阴影和额外 pass 计绘制，不承诺全场只有一次 draw call；大范围实例需要分区保持裁剪能力。
- **轻量可复放动效**：摆动、滴落、局部波纹与设备运动优先使用解析函数；偶发行为使用带种子的调度与 FSM。数学动效有明确触发、停止和功能含义。仅在交互确实需要碰撞与约束时评估物理引擎。
- **局部程序资产和纹理**：管线、栏杆、重复硬表面及标识适合参数化几何和 CanvasTexture / DataTexture。正文、可操作名称与必要状态保留 DOM 可达表达。人物、重点设施是否采用 GLB 取决于造型质量与成本，不设置“98% 纯代码”或“零外部图片”指标。

### 按视觉需要采用，并修正实现表述

| 原建议 | 使用条件与技术修正 |
|---|---|
| 2–3 阶 Toon 光照 + 青色半球补光 | 可用于风格化试样，量化只建立明暗分区，不能单独产生水彩感。配色、边缘、材质与局部接触阴影需一起设计；强补光可能抹平体积。自定义 ShaderMaterial 不会自动获得完整 Three.js 光照与阴影，需明确集成或自行实现。 |
| 深度／法线 Sobel 轮廓线 | 近景重点物件确需轮廓时评估。法线与深度成本取决于预通道／缓冲复用方案，须测量完整管线 GPU 开销、细节噪声、透明物体处理与移动端效果；不默认全场开启。Inverted Hull 也会增加绘制和遮挡问题。 |
| 色块水面、深度吸收和水洼 | 只有场景确需水时实现。先明确环境贴图或平面反射等反射来源；压低粗糙度不会凭空产生现场倒影。Beer–Lambert 需要水中光路长度，线性化深度差只是特定视角和几何条件下的近似。阶梯边界用导数抗锯齿，不把 floor 本身当作抗锯齿。 |
| 船体四点采样浮动 | 小幅风格化浮动可采用共享 H(x,z,t)。完整 Gerstner 包含水平位移，CPU 采样需与 GPU 参数和坐标一致；简单高度函数并非任意 Gerstner 表面的精确反解。 |
| 每帧更新缆绳 | 避免每帧新建 TubeGeometry。保持拓扑，更新预分配顶点或使用顶点变形。sag=max(0,L-d) 只是松弛程度的启发式，不能保证曲线弧长为绳长；真实约束需另求解。 |
| 光柱、焦散与多层玻璃 | 只有明确的光源、受光面和视线关系时使用。透明锥体是光柱近似；噪声自发光是装饰性近似，需限制在合理区域。depthWrite=false 不保证玻璃正确排序或消除透明相交问题，仍需深度测试、排序及薄表面方案。 |

### 不转化为需求

港口、渔船、雨景、生态缸切片、高调水彩、全局描边、百件资产数量以及纯程序建模比例，都不因技术说明出现而进入首页验收范围。并行开发只在任务可独立拆分且获得明确授权时使用；其收益来自共享契约和集成检查，不能保证美术一致性或资产精度。

当前仅完成技术取舍记录，没有将以上可选效果接入场景。实施顺序：先校准关键构图与人物／设施造型，再用代表物件试材质和受光；通过视觉评审后制作一个交互片段，最后按测量增加必要效果。功能、性能与美术分别验收。
