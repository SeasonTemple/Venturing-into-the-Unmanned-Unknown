## 逐项取舍

| 建议 | 当前决定 | 如何落实 |
|---|---|---|
| 灯光、模型、相机、后处理、入口模块分离 | 采纳 | 另将任务规则与渲染分离，避免画面逻辑决定验收结果 |
| 一处管理 renderer、resize、循环与 dispose | 采纳并补全 | resize 使用容器尺寸；后台暂停；取消 RAF；释放监听与 GPU 资源；重复进入退出可验证 |
| 加载状态与错误退路 | 采纳 | 进入准备期间保留正常首页；失败能阅读和重试，减少动态效果不阻断任务 |
| 控制相机范围，避免穿模 | 采纳 | 短进入路径、明确落点；转场与用户控制不同时写相机 |
| GLB、纹理优化、性能量测 | 采纳 | 精模阶段先检查资产，再选压缩；记录多 pass 绘制、帧间隔、传输与 GPU 资源 |
| 桌面与移动分别取景，限制 DPR | 采纳 | 桌面 ≤2、移动 ≤1.5，窄屏布局和阅读面独立检查 |
| 使用 Next.js + R3F 替换现有框架 | 当前不采纳 | 延续既有 Astro 与原生 Three.js，先完成灰盒闭环，再依据实际维护问题评估 |
| 强制 HDRI city/sunset、Bloom、暗角、自动旋转 | 改为按任务选择 | 灰盒先用一处主投影光和补光；不加入无意义循环、强发光或遮蔽信息的后处理 |
| 每个大模型都运行 gltfjsx 并视为启用 Draco | 调整 | gltfjsx 是 React 组件工具；原生资产不需要转 JSX。压缩类型以实际导出扩展及解码依赖为准，不能仅凭 `-T/-t` 推断 |
| 开发调试面板 | 按需 | 灰盒先暴露最少量可读状态；确需参数 GUI 时再增加依赖，生产界面不带调试工具 |
| 安装 DSH 插件与 VS Code 扩展 | 暂不安装 | 当前运行环境及需求未证明需要；文中列出的第三方插件可用性与能力未独立验证 |

## 示例代码需要补充的地方

- 示例 `dispose()` 没有取消递归 RAF。释放 renderer 后仍调度渲染会造成异常或重复循环。
- 释放 material 不会自动释放它引用的全部纹理；环境贴图、PMREM 目标、阴影、后处理 render target 和加载器资源须按所有权清理。
- 控制器、ResizeObserver、文档事件与异步加载结果需要撤销或作废。
- 共享纹理与几何要避免被一个模块提前释放；不能把 R3F 的自动处理理解为所有资源均有通用引用计数。
- 后处理的输出色彩与 tone mapping 要有明确管线，不重复套用色调映射。单一 renderer 的正常渲染和 composer 不是同时各画一遍。
- 原生手写并不天然更快，R3F 也不天然更可靠；应以实际结构、负载与检查结果判断。

## 第一版执行边界

先做一个独立、可打开的 Three.js 灰盒原型：正常预览入口 → 进入 → 相同中继任务的两种职责 → 一章真实内容 → 使用检查方法 → 局部恢复 → 相同环境变化 → 返回。

首版不引入新框架、外部 LLM、付费模型或未经核验插件。保留可复放的任务规则、键盘入口、静态降级和明确的证据状态。精模、GLB 压缩、HDRI 与复杂后处理放到路径得到验证之后。
